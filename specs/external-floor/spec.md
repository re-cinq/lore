The Floor was rewritten as a standalone engine ([re-cinq/floor](https://github.com/re-cinq/floor)) that stores assembly-line definitions, walks runs, queues work and serves a live socket, and that holds no GitHub client and never calls out. This spec is the first slice of replacing `apps/floor` with it ([ADR-049](../../adrs/ADR-049-external-floor.md)): the three code-review lines run on the external floor, reached only through `@re-cinq/floor-client`, while every other line stays on `apps/floor` until its own slice.

## Background

The external floor assigns three jobs to whoever owns GitHub: start its lines, run a service station for every GitHub action a line takes, and answer its git-credential request. Lore owns GitHub, so those three jobs are this spec. Both floors run side by side: a run is either in `pipeline.assembly_runs` (Lore's Floor) or in the external floor's own database, and the run page reads both.

- FR8.1 — `feature-planning` is a floor pipeline file, `libs/assembly-lines/src/floor-pipelines/feature-planning.yaml`, in the same shape as the review lines: it walks `analyze → plan-pass-end → author → analyse-specs → qa-generate ⇄ qa-questions → draft → split-sections ⇉ write → assemble → qa-answer → qa-gate → open-spec-pr → merged → decompose → issues → issue-coverage → done` (a `qa-gate` that gave up forks to `spec-findings → author` instead of opening the PR, `specs/7-feature-planning` FR-24.20), with `validate` reached only by its own `manual.plan.validate` start event rather than an edge, and `plan_id` is its only subject. ([validated by turns a run a start by hand reopened into a running run status](../../apps/lore-api/src/work/floor/floor-frames.test.ts#L84), [validated by sends nothing for a frame type the floor adds later, rather than throwing](../../apps/lore-api/src/work/floor/floor-frames.test.ts#L95))
- FR18.11 — _(Added 2026-10-07.)_ A channel the server keeps closing is given up on, not re-opened for as long as the page is up. A close the server may recover from (`server`, `slow`, a token that could not be fetched) was answered with a flat one-second re-open and no attempt count, while the SOCKET path had escalation and a give-up all along; so a server failing the same way on every open was re-opened once a second indefinitely, and because each open replays the run's whole snapshot, the plan page refreshed on every cycle (FR18.10 is one frame that caused exactly this). The channel now carries its consecutive closes, takes its pause from the socket's own backoff — 1s, 2s, 4s, 8s, 16s — and after five goes `offline`, which the page already renders. One successful open forgets them. **Each waiting channel's retry is its own**: the `schedule_retry` effect and the `retry_due` event both carry the channel's id, and the client holds one timer per channel beside the socket's. The socket's own retry is the one that carries NO channel, and only that one connects a backed-off socket — a channel's firing while the socket waits leaves it waiting, or a 1s channel would start a socket that owed 16s. A single shared timer would have defeated the schedule it escalates — the first channel's pause woke every waiting channel, so a 1s retry opened a channel that owed 16s, and the socket's own 1s reconnect was blocked behind whichever channel had armed the timer first (a plan page holds two channels, so this was the normal case, not the corner). ([validated by escalates the pause and gives up after five server closes, instead of re-opening forever](../../apps/web-ui/src/lib/live-socket/connection-machine.test.ts#L230), [validated by forgets the failed attempts once the channel opens again](../../apps/web-ui/src/lib/live-socket/connection-machine.test.ts#L322), [validated by opens only the channel whose own retry came due, leaving another still waiting](../../apps/web-ui/src/lib/live-socket/connection-machine.test.ts#L255), [validated by schedules a channel's retry under that channel's own id, so the socket's timer is its own](../../apps/web-ui/src/lib/live-socket/connection-machine.test.ts#L310), [validated by leaves a backing-off socket alone when a channel's own retry fires](../../apps/web-ui/src/lib/live-socket/connection-machine.test.ts#L288), [validated by connects a backing-off socket when its own retry fires, which carries no channel](../../apps/web-ui/src/lib/live-socket/connection-machine.test.ts#L299))

## Upgrading a run's assembly line

- FR19.1 — _(Added 2026-10-07.)_ A run is pinned to the version of its line that existed when it started. - FR19.2 — `GET /api/assembly-runs/{id}/upgrade` (scope `read`) answers `{ available }` by comparing the floor's current version of the run's line against the hash the run carries, and 404 for a run the floor does not have (`apps/lore-api/src/work/floor/upgrade-run.ts`). - FR19.3 — `POST /api/assembly-runs/{id}/upgrade` (scope `task`) starts the current version with the source run's complete start-item bag, pinning the version it read, and answers 201 `{ run_id }`; the web tier passes that answer to the browser as JSON and the button opens the run, because a redirect built in the web pod would carry the pod's own origin. The floor ignores inputs a newer line no longer needs and validates inputs it newly needs. A source run that is still open is cancelled first, reason `upgraded to the latest assembly line` — the floor answers a start on a subject that already has an open run by joining that run, so without the cancel the upgrade would hand back the old run on the old version; a run that already finished is not cancelled again.
