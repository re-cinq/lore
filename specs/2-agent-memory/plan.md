## Architectural Pivots

Several scope decisions changed between this plan and the shipped
implementation. The original five-phase plan was accurate through
Phase 1. Phases 2 and 3 diverged significantly.

| Original Plan | As Built | Reason |
|---------------|----------|--------|
| `shared_write` / `shared_read` MCP tools | `shared_pools` table only; writes via `lore_write_memory(pool_id=...)` | Explicit pool tools added friction; pool scoping via existing `lore_write_memory` proved sufficient |
| `create_snapshot` / `restore_snapshot` MCP tools | Tables exist (`memory.snapshots`) but no MCP tools exposed | Snapshot restore not used in practice; focus shifted to importance decay + consolidation as the recovery strategy |
| `agent_health` + `lore_agent_stats` (two tools) | Single `lore_agent_stats` tool | Health info folded into stats response |
| No episode concept | `lore_write_episode` tool + `memory.episodes` table | Passive ingestion of raw conversation text was added per ADR-014; episodes are the primary source for automatic fact extraction |
| No knowledge graph | `lore_query_graph` tool + `memory.entities` + `memory.edges` | Graphiti/FalkorDB evaluation (spec 1) showed PostgreSQL graph tables were sufficient; replaces the static `graphrag/graph.json` |
| Simple `memory.facts` (fact_text + embedding) | Facts with temporal validity, confidence tiers, retrieval metadata, conflict detection | ADR-014 and production usage revealed facts needed lifecycle management |
| `lore_assemble_context` not planned here | `lore_assemble_context` as a top-level MCP tool | Reduces multi-tool call overhead; replaces pattern of calling `lore_search_context` + `lore_search_memory` + `get_adrs` separately |
| Web UI: Phase 3 (memory browser + pools + audit trail) | Web UI ships read-only memory browser + agent overview; pipeline/task UI took priority | Memory UI is functional but full audit trail and pools browser deferred |
| File-backed fallback: simple JSON | File-backed fallback: implemented as planned | No change |

## Implementation Phases

### Phase 1: Memory MCP Tools — COMPLETE

#### 1.1 Agent ID Generation

**Files:** `mcp-server/src/agent-id.ts`, `scripts/install.sh`

Resolution order (as implemented):
1. Explicit `agent_id` parameter on any tool call.
2. `LORE_AGENT_ID` env var (Lore Agent pods set this to pod name).
3. `~/.lore/agent-id` file.
4. Auto-generate UUID, write to `~/.lore/agent-id`.

`install.sh` creates the file on fresh install. `lore-doctor.sh`
checks the file exists.

#### 1.2 PostgreSQL Schema (`memory` schema)

Applied via `scripts/infra/setup-memory-schema.sh`. All tables in a
`memory` schema within the existing `lore` database on `lore-db-1`.

**`memory.memories`** — core key-value store

| Column       | Type           | Notes |
|--------------|----------------|-------|
| id           | UUID PK        | `gen_random_uuid()` |
| agent_id     | TEXT NOT NULL  | Indexed |
| repo         | TEXT           | Nullable; scopes memory to a repo |
| key          | TEXT NOT NULL  | |
| value        | TEXT NOT NULL  | |
| embedding    | VECTOR(768)    | Nullable, async fill |
| version      | INTEGER        | Monotonic, starts at 1 |
| is_deleted   | BOOLEAN        | Soft delete |
| ttl_seconds  | INTEGER        | Nullable |
| expires_at   | TIMESTAMPTZ    | Nullable |
| created_at   | TIMESTAMPTZ    | DEFAULT now() |
| pool_id      | UUID           | FK to shared_pools; nullable |
| half_life_days | INTEGER      | Decay parameter for importance scoring |
| retrieval_count | INTEGER     | Incremented on every search hit |
| last_retrieved_at | TIMESTAMPTZ | Updated on search hit |

- UNIQUE on `(agent_id, key, version)`.
- HNSW index on `embedding` for vector search.
- Partial index on active memories.

**`memory.memory_versions`** — full version history

Every write creates a row. `memories` holds the latest state.

**`memory.facts`** — extracted factual statements

| Column           | Type           | Notes |
|------------------|----------------|-------|
| id               | UUID PK        | |
| memory_id        | UUID FK        | Parent memory |
| episode_id       | UUID FK        | Parent episode (nullable) |
| fact_text        | TEXT NOT NULL  | Single self-contained statement |
| embedding        | VECTOR(768)    | |
| confidence       | TEXT           | `verified` / `observed` / `inferred` / `stale` |
| valid_from       | TIMESTAMPTZ    | When this fact became true |
| valid_to         | TIMESTAMPTZ    | Nullable; set on invalidation |
| retrieval_count  | INTEGER        | |
| last_retrieved_at | TIMESTAMPTZ  | |
| half_life_days   | INTEGER        | |
| created_at       | TIMESTAMPTZ    | |

- GIN index on `fact_text` for BM25 keyword search.
- HNSW index on `embedding`.
- When a new fact contradicts an existing one (cosine similarity >= 0.92),
  the old fact's `valid_to` is set and a record is written to
  `memory.fact_conflicts`.

**`memory.fact_conflicts`** — contradiction log

| Column       | Type     | Notes |
|--------------|----------|-------|
| id           | UUID PK  | |
| old_fact_id  | UUID FK  | Invalidated fact |
| new_fact_id  | UUID FK  | Replacement fact |
| similarity   | FLOAT    | Cosine similarity that triggered conflict |
| created_at   | TIMESTAMPTZ | |

**`memory.episodes`** — raw text blobs

| Column       | Type     | Notes |
|--------------|----------|-------|
| id           | UUID PK  | |
| agent_id     | TEXT     | |
| repo         | TEXT     | Nullable |
| content      | TEXT     | Raw text (conversation, review, observation) |
| source       | TEXT     | e.g. `session`, `task`, `review` |
| embedding    | VECTOR(768) | |
| created_at   | TIMESTAMPTZ | |

Facts and graph entities are automatically extracted from episodes.

**`memory.entities`** — knowledge graph nodes

| Column       | Type     | Notes |
|--------------|----------|-------|
| id           | UUID PK  | |
| name         | TEXT UNIQUE | Normalized lowercase |
| entity_type  | TEXT     | `service` / `team` / `technology` / `concept` / `person` |
| created_at   | TIMESTAMPTZ | |

**`memory.edges`** — knowledge graph relationships

| Column       | Type     | Notes |
|--------------|----------|-------|
| id           | UUID PK  | |
| source_id    | UUID FK  | entities.id |
| target_id    | UUID FK  | entities.id |
| relation     | TEXT     | `uses` / `owns` / `depends-on` / `replaced-by` / `part-of` / `implements` |
| valid_from   | TIMESTAMPTZ | |
| valid_to     | TIMESTAMPTZ | Nullable |
| episode_id   | UUID FK  | Episode that introduced this edge |

**`memory.snapshots`** — reference-based snapshots (table exists; no MCP tools exposed)

**`memory.shared_pools`** — named cross-agent pools (referenced via `memories.pool_id`)

**`memory.audit_log`** — immutable operation log

Append-only. Indexed on `(agent_id, created_at)`.

#### 1.3 MCP Memory Tools (as shipped)

**`lore_write_memory`**

```typescript
{
  key: z.string(),
  value: z.string(),
  agent_id: z.string().optional(),
  ttl: z.number().optional(),
  extract_facts: z.boolean().optional(),
  repo: z.string().optional()
}
```

Returns `{ key, version, agent_id, created_at }`.

Privacy filter (`sanitizeContent()` / `redactSecrets()`) runs before
storage. Embedding generated synchronously via Vertex AI. If
`extract_facts = true`, fact extraction runs async (never blocks write).

**`lore_read_memory`**

```typescript
{
  key: z.string(),
  agent_id: z.string().optional(),
  version: z.string().optional()   // "all" or specific version number
}
```

**`lore_delete_memory`**

Soft-delete (`is_deleted = TRUE`). Version history preserved.

**`lore_list_memories`**

```typescript
{
  agent_id: z.string().optional(),
  limit: z.number().default(50),
  offset: z.number().default(0)
}
```

Returns only active (not deleted, not expired) memories.

**`lore_search_memory`**

```typescript
{
  query: z.string(),
  agent_id: z.string().optional(),
  pool: z.string().optional(),
  limit: z.number().default(10),
  include_invalidated: z.boolean().optional()
}
```

Hybrid search (HNSW vector + BM25 keyword) over `memories.embedding`
and `facts.embedding`, merged via Reciprocal Rank Fusion. Results
capped at max 3 per `(agent_id, source)` combo to prevent one verbose
session dominating results. Returns confidence annotations. Stale
facts get a -1 importance penalty.

Every search hit asynchronously increments `retrieval_count`,
updates `last_retrieved_at`, and extends `half_life_days` (+2, cap
365). Stale facts revive to `observed` on retrieval.

**`lore_write_episode`**

```typescript
{
  content: z.string(),
  agent_id: z.string().optional(),
  repo: z.string().optional(),
  source: z.string().optional()
}
```

Ingests raw text (conversation turn, code review, observation).
Automatically extracts facts and updates the knowledge graph. Triggers
the same privacy filter as `lore_write_memory`. The primary input path for
passive memory capture (ADR-014).

**`lore_query_graph`**

```typescript
{
  entity: z.string(),
  depth: z.number().default(1)
}
```

Returns entities and relationships from the live knowledge graph.
Replaced the static `graphrag/graph.json`.

**`lore_assemble_context`**

```typescript
{
  query: z.string(),
  repo: z.string().optional(),
  template: z.string().optional(),  // default | review | implementation | research
  max_tokens: z.number().default(8000)
}
```

Top-level tool that assembles context from all sources (repo chunks,
ADRs, memories, facts, episodes, graph) into a single token-budgeted
block. Replaces the prior pattern of calling `lore_search_context` +
`lore_search_memory` + `get_adrs` individually. Research template keeps
16K tokens; implementation/review/default cap at 8K.

**`lore_agent_stats`**

```typescript
{ agent_id: z.string().optional() }
```

Returns: `{ agent_id, memory_count, episode_count, total_facts,
total_searches, daily_breakdown (last 7 days) }`. Health info
(last active, oldest memory) folded in. Aggregated from `audit_log`.

#### 1.4 File-Backed Fallback

**File:** `mcp-server/src/memory-file.ts`

When PostgreSQL is unavailable, tools fall back to JSON files in
`~/.lore/memory/<agent-id>/`. Search degrades to case-insensitive
substring matching. Fact extraction is skipped. Transparent to
callers — each handler checks `isMemoryDbAvailable()` first.

Shared pools fall back to `~/.lore/memory/shared/<pool-name>/`.
Cross-machine sharing requires PostgreSQL.

### Phase 2: Advanced Features — COMPLETE

#### 2.1 Fact Extraction (`mcp-server/src/facts.ts`)

Async extraction triggered by `lore_write_memory(..., extract_facts: true)`
or automatically on every `lore_write_episode` call.

LLM configuration:
- `LORE_FACT_LLM`: `claude` (default) / `openai` / `ollama`
- `LORE_FACT_MODEL`: `claude-haiku-4-5-20251001` / `gpt-4o-mini` / `llama3`
- `LORE_OLLAMA_URL`: for local Ollama

Retry: 3 attempts with exponential backoff (1s, 3s, 9s). If all
fail, the memory is searchable as raw text. Writes never blocked.

Cost tracking: `pipeline.llm_calls` row per extraction (model,
tokens, cost_usd, duration_ms).

#### 2.2 Knowledge Graph (`mcp-server/src/graph.ts`)

Entity and relationship extraction runs on every `lore_write_episode`
call alongside fact extraction. LLM prompt extracts up to 10
entities and 10 edges per episode. Entity names normalized to
lowercase for deduplication.

Edges carry `valid_from` (episode creation time) and nullable
`valid_to` for temporal tracking of relationship changes.
`lore_query_graph` traverses the live graph instead of the old static
`graphrag/graph.json`.

#### 2.3 Passive Session Capture (ADR-014)

**File:** `mcp-server/src/session-tracker.ts`

Tracks all MCP tool calls in a 500-entry in-memory ring buffer. On
process exit, dumps to `~/.lore/last-session.json`. The stop hook
installed by `install.sh` POSTs to `/api/session-summary`, which
runs automatic episode + fact extraction from the session dump.
Zero agent cooperation needed — passive by design.

#### 2.4 Post-Task Auto-Curation (ADR-014)

**File:** `agent/src/lib/episode-writer.ts`

After every task completion (PR created, no-changes, failure,
feature-request, onboard), an episode is written automatically.
For high-signal events, Haiku extracts a "lesson learned" stored
as a `auto-curation/{ref}` memory entry. Enables passive learning
across task runs.

#### 2.5 Importance-Based Memory Decay (ADR-014)

**File:** `agent/src/jobs/memory-lifecycle.ts`

Daily job (5 AM UTC) scores memories 0–10:
- Recency: -1 per 30 days of age
- Content quality: short (<50 chars) penalized, long (>500) boosted
- Key pattern: `decisions/` and `conventions/` keys +2; `auto-curation/` and `sessions/` -1
- Stale confidence tier: -1

Evicts lowest-scoring entries when an agent exceeds 500 memories.
Transitions unretrieved facts to `stale` confidence after 30 days.
Cleans invalidated facts older than 30 days when total exceeds 2000.

Also runs automatic fact consolidation (5:30 AM UTC): groups recent
facts (7-day lookback) by repo, calls Haiku to extract 1–3 patterns
per repo, stores as `consolidated/{repo}/{timestamp}` memories.
Requires minimum 5 facts per repo to trigger.

#### 2.6 Confidence Tiers and Conflict Detection

Facts carry a `confidence` column: `verified` (human-confirmed),
`observed` (episode-sourced, default), `inferred` (memory-sourced),
`stale` (unretrieved 30+ days). Assembled context and search results
include confidence annotations.

When a new fact contradicts an existing one (cosine similarity >=
0.92), the old fact's `valid_to` is set, its confidence becomes
`stale`, and a record is written to `memory.fact_conflicts`.
`lore_assemble_context` prefixes `[CONFLICT]` on facts with recent (7-day)
conflicts to give agents visibility into disputed knowledge.

#### 2.7 Retrieval Strengthening

Every `lore_search_memory` call asynchronously increments
`retrieval_count`, updates `last_retrieved_at`, and extends
`half_life_days` (+2, cap 365) on returned facts and memories.
Stale facts revive to `observed` on retrieval. Fire-and-forget —
adds zero latency to search results.

#### 2.8 TTL and Expiration

In-process scheduled job (hourly) runs hard deletes 24 hours after
`expires_at`. Expired memories excluded from search immediately via
partial index.

#### 2.9 Phase 2 Verification (as verified)

- `lore_write_memory(key: "notes", value: "ADR-042 mandates integer cents...", extract_facts: true)` — returns immediately, facts appear within seconds.
- `lore_search_memory(query: "currency format")` — returns fact "ADR-042 mandates integer cents" (not the full paragraph).
- Contradiction: writing a new fact that conflicts with an existing one creates a `fact_conflicts` row and invalidates the old fact.
- `lore_write_episode(content: "session transcript...", source: "session")` — facts and graph entities extracted automatically.
- `lore_query_graph(entity: "payments-service")` — returns live relationships from episode-derived graph.
- Passive capture: session dump POSTed on stop hook, episode written, facts extracted without agent action.
- Lifecycle job evicts lowest-scoring memories when agent exceeds 500 entries.
- Consolidation job extracts patterns from 7-day fact window.

## Risk Register (Final Status)

| Risk | Impact | Outcome |
|------|--------|---------|
| Embedding latency on write (Vertex AI round-trip) | Medium | Mitigated: embeddings are synchronous but fast enough (<50ms p95). Async option not needed. |
| Fact extraction LLM unavailable | Low | Mitigated: retry queue works as designed. Memory searchable as raw text during outages. |
| File-backed fallback feature drift | Medium | Mitigated: shared test suite runs against both backends in CI. |
| Schema migration on existing CNPG | Medium | Resolved: `memory` schema additions are fully additive. No existing table modified. |
| Snapshot restore correctness | Medium | Deferred: snapshot restore MCP tools not exposed. Tables exist for future use. |
| Agent ID collision | Low | Non-issue in practice: UUID v4 collision probability negligible. |
| Fact contradiction false positives | Medium | Threshold 0.92 cosine similarity chosen empirically. False positive rate acceptable in production. |

## Critical Path (Actual)

```
Agent ID generation + memory schema DDL (Phase 1, day 1)
  -> lore_write_memory + lore_read_memory (Phase 1, day 2)
    -> lore_search_memory with embeddings (Phase 1, day 3)
      -> file-backed fallback (Phase 1, day 4)
        -> fact extraction (Phase 2, day 1)
          -> lore_write_episode + knowledge graph (Phase 2, day 2)
            -> confidence tiers + conflict detection (Phase 2, day 3)
              -> passive session capture (ADR-014, Phase 2, day 4)
                -> memory lifecycle: decay + consolidation (Phase 2, day 5)
                  -> lore_assemble_context tool (Phase 2, day 6)
                    -> retrieval strengthening (Phase 2, day 7)
                      -> Web UI: agent overview + memory browser (Phase 3)
```

The addition of `lore_write_episode` and the knowledge graph in Phase 2
shifted the critical path significantly from the original plan.
These were not blocking but became foundational for `lore_assemble_context`
performance.
