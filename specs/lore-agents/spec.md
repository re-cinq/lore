# Feature Specification: Agent definitions as data

| Field    | Value                          |
|----------|--------------------------------|
| Feature  | Agent definitions as data      |
| Branch   | feat/lore-agents-table         |
| Status   | In Progress                  |
| Created  | 2026-06-16                     |
| Owner    | Platform Engineering           |
| ADR      | ADR-024                        |

This spec promotes per-task-type agent behaviour — model, timeout, prompt, and container image — out of the hardcoded `task-types.yaml` into a first-class `lore.agent_definitions` table with per-repo overrides, a dedicated Agents settings tab, and a `/lore-agents` skill, so operators can retune a repo's agents without a source edit and redeploy. Since 2026-10-31 (#3995) the external floor is the only store of agent definitions: the org default is a floor definition's `settings`, a repo's override its entry in `variants`, and the `lore.agent_definitions` table was dropped (migration 0122). Where this spec still names the table, it records how the feature was first built.

## Why

Per-task-type behaviour (model, timeout, prompt, container image) was hardcoded
in `scripts/task-types.yaml` and only thinly overridable per repo via a JSONB
blob. Operators could not define or retune a repo's agents without a source edit
and redeploy. This promotes **agent definitions** to first-class, per-repo data
— a real `lore.agent_definitions` table, a dedicated **Agents** settings tab, and
a `/lore-agents` skill — reached only through the `project.agentDefs` port (the
config side; `project.agents.run()` stays the execution side). See ADR-024
([Agent definitions as data](../../adrs/ADR-024-ubiquitous-language-execution-model.md#agent-definitions-as-data)).

- Every project uses different programming languages; the base image selector lets an operator set the execution image once for the whole repo and have every assembly line respect it automatically, rather than setting the same value on each agent type individually. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#intent-p-1))
- Today, Lore ships one global default execution image for all agent nodes; a repo can override it, but only one agent type at a time — a Node.js repo that needs a custom image must set the same value on every agent type it uses, with no single place to say "this repo runs from this image" and have every assembly line respect it automatically. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#intent-p-4))
- When set, the repo base image becomes the execution image for every agent node in every assembly line running in that repo, unless a specific agent type carries its own override; the resolution order is agent-level override → repo base image → org default, and nothing about individual agent overrides changes. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#intent-p-5))

## Scope

In (this PR): the `lore.agent_definitions` table; resolution (project → org → yaml)
via `project.agentDefs`; the agent-definitions HTTP API; the per-repo **Agents**
nav tab (list with
org/project labels + dedicated new/edit form pages with breadcrumbs); the `/lore-agents` skill; floor + runner
resolution through the port.

Out (Phase 2): the `.lore/workflows/` loader (repo > built-in) and the workflow
`on:` triggers + event-dispatch registry. The agent carries neither a `workflow`
nor a `trigger` column — both belong on the workflow.

## Data model

An agent definition is a floor definition of kind `agent_definition`, read and written
through `@re-cinq/floor-client`: its `settings` (`model`, `prompt`, `image`,
`timeoutMinutes`, `config`) are the organisation default, and its `variants` map
holds one entry per repo override, keyed `github.com/<owner>/<repo>`. Until
2026-10-31 the same data lived in a `lore.agent_definitions` table (migrations
0015 and 0016, an org row with `project_id = NULL` and one row per repo override);
migration 0122 drops it.

The `base_image` key is a new field in the `lore.repos.settings` JSONB column (`libs/shared/src/domain/models/repo-settings.ts`). It is max 256 characters, has the same character-set validation as the per-agent image field, and accepts only values from the platform-published approved-image list. Null or absent means no repo base image is set. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#scope-p-2))

## Requirements

- **FR1 — Port-only access.** Agent-definition config is reached only through
  `project.agentDefs` (`resolve`/`list`) and `project.agentDefsWriter` (`create`/`update`/`delete`); no consumer

## Success Criteria

- **SC-001 (Base Image Adoption):** Measures whether the feature is actually solving the problem — teams with active lines and polyglot toolchains should gravitate to a base image rather than repeating per-agent overrides: 30% of repos with an assembly line run in the past 30 days set a repo base image within 90 days of GA. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#k-base-image-adoption))
- **SC-002 (Per-Agent Redundancy Decrease):** A proxy for the problem being solved — these repos were manually repeating one image across every agent type because no base image existed; decline signals consolidation onto the new setting: repos where 3+ individual agent image overrides share the same image value decrease by 50% within 90 days of GA. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#k-per-agent-redundancy))

## Constraints

- **No half-shipped state:** The UI control, resolution logic, and effective-image display must ship together as one atomic change; a setting that exists but is silently ignored at dispatch is worse than no setting — it gives operators false confidence. The primary UI surface is `apps/web-ui/src/app/repos/[owner]/[repo]/agents/`. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#constraints-p-4), [from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#delivery-p-1))
- **Resolution at dispatch:** The external floor resolves the base image at the moment it dispatches each node, not at run start; the base image must flow through `libs/shared/src/outbound/floor/floor-client.ts` — the existing path the floor already uses to resolve agent configuration — so runner pods see the correct value without any new protocol or API call. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#constraints-p-2))
- **Two-key exemption:** The repo base image setting is NOT governed by the two-key approval ceremony; `apps/lore-api/src/transport/routes/repos/repo-settings.ts` does not call `checkApproval` from `apps/lore-api/src/transport/routes/two-key.ts` for `base_image` writes, and `verifyApproval` in `apps/lore-api/src/work/two-key/approval-pr.ts` is not invoked for this setting. Authorization is the same admin scope that already governs agent-definition writes for the repo — no additional ceremony or approval PR is required; `apps/lore-api/src/transport/routes/repos/repo-settings.ts` accepts and persists `base_image` with no two-key gate (not on main). There is no feature flag or phased rollout needed; adoption is paced by each repo's operator at their own pace. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#constraints-p-1), [from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#delivery-p-4))

- **Fallback must not change:** The org-wide default image — the floor definition's `settings`, resolved by `libs/shared/src/outbound/project/agents/agent-defs-floor.ts` — is the fallback of last resort. This feature adds the repo base image as a new middle layer above it; it must not modify the org default or the way it resolves when neither a per-agent override nor a repo base image is set. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#constraints-p-3))

- **Additive and backward-compatible:** Repos with no `base_image` key in `lore.repos.settings` continue to resolve the execution image exactly as today — `agent.image ?? org_default` through `libs/shared/src/outbound/project/agents/agent-defs-floor.ts` — with no behavioral change. `libs/shared/src/domain/models/repo-settings.ts` (`RepoSettingsSchema`) uses `passthrough()` so the absent key causes no error on repos that have not opted in. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#delivery-p-2))
- **Existing per-agent overrides unaffected:** Repos that already set `image` on an agent's floor variant keep those values and their precedence as the top layer of the three-layer resolution; the two-key gate on those writes is also unchanged. Migrating to a repo `base_image` is voluntary and at each operator's own pace, with no forced change. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/99260c66-0f94-44fb-b9f4-88058eeeee4a#delivery-p-3))

## Resolved Questions

Each question the plan raised is answered by the statements above.

- Station nodes: the base image applies to every pod the floor dispatches, agent and station nodes alike (FR-BASE-RESOLUTION).
- Curated list or free text: only platform-published approved images are offered; free-form text is not allowed (FR-BASE-UI).
- Where it appears: the Agents tab is the primary surface, with a shortcut on the repo's general settings page (FR-BASE-UI).
- Two-key ceremony: it does not apply to the repo base image (Constraints, "Two-key exemption").
- Authorization instead: the same admin scope that governs agent-definition writes (FR-BASE-SETTING).
