# Feature Specification: Shared organisation skills

| Feature | Shared organisation skills  |
| ------- | --------------------------- |
| Branch  | org-skills                  |
| Status  | In Progress                 |
| Created | 2026-10-13                  |
| Owner   | Platform Engineering        |

Org-managed skills are dynamic, database-backed, and automatically distributed to local developer machines by the local MCP server, replacing the static `apps/mcp-server/agent-skills/` directory as the source of truth for org-wide Claude Code skills.

## Problem Statement

Currently, skills are baked statically into `apps/mcp-server/agent-skills/` and distributed via local setup scripts or the HTTP gateway. We need to move this to a dynamic, database-backed system managed from the Lore web UI, enabling automatic updates to active developer environments without manual re-installation. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#p_809dfdf5-6aa1-44b9-8803-b1589b0fdb06))

## Requirements

### Functional Requirements

- **FR-001**: The system MUST persist dynamic organisation skills in the `lore.skill_definitions` table, created by a migration `NNNN_skill_definitions.sql` (the next free slot; `0110_utopia_memory_mirror.sql` is the last one today) under `infra/terraform/modules/gke-mcp/lore-platform/charts/ui-helm/migrations/`, with columns: `name` (skill directory name), `title`, `description`, `model` (optional; same curated model IDs as agent definitions), `content` (the SKILL.md body text), `enabled` boolean, and `project_id` (reserved for future per-repo overrides; all v1 rows use NULL for org-wide scope). ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-2), [validated by this](apps/lore-api/src/integration-tests/skill-definitions-migration.acceptance.test.ts#L23), [validated by](apps/lore-api/src/migrations.test.ts#L31), [validated by accepts null for optional model and projectId fields](libs/shared/src/domain/models/skill-definition.test.ts#L12))
- **FR-002**: The web UI MUST provide a "Skills" management page modelled on the Agents page (`/agents`) — list, create, edit, and delete for org-level skill definitions in v1 — implemented under `apps/web-ui/src/app/` following the `apps/web-ui/src/app/agents/` reference pattern; the per-repo override tab (the `/repos/[owner]/[repo]/agents` equivalent) is deferred to a later version. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-5), [from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#p_3e468b00-52df-4688-b922-1d337e2d70b6))
- **FR-003**: Skill definitions offer options for setting models, titles, and any other options available in Claude skills. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#intent-p-1))
- **FR-004**: This feature adds local file-system writes for Claude configuration (under `~/.claude/skills/`) to `apps/mcp-server`'s responsibilities; the local MCP server MUST automatically install, update, and remove org skills on developer machines via a new module `apps/mcp-server/src/transport/skills-sync.ts` that polls `/api/skill-definitions` on a configurable interval, writes each enabled skill as `~/.claude/skills/<name>/SKILL.md` with a `~/.claude/skills/<name>/.lore-managed` ownership marker (see Constraints), and deletes any `.lore-managed` skill directory whose skill has since been disabled or deleted upstream; this introduces local file-system writes for Claude config as a new responsibility for `apps/mcp-server`, which currently only proxies HTTP to `LORE_API_URL`; the module is gated on `serverMode !== 'agent'` (same gate used by `lore_update` in `apps/mcp-server/src/transport/build-mcp-server.ts`), because the HTTP gateway has no `~/.claude/` tree. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-6), [from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#p_c85b6e0d-8249-4e32-b840-922f18f74438))

- **FR-005**: The domain model for `lore.skill_definitions` MUST be defined in `libs/shared/src/domain/models/skill-definition.ts` (added by this feature) as a Zod schema with `ColumnMap` + `fromRow`/`selectList` helpers, following the pattern of the existing model files in `libs/shared/src/domain/models/` (e.g. `libs/shared/src/domain/models/agent-definition.ts`). ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-3)) ([validated by validates and deserializes skill definition rows.](libs/shared/src/domain/models/skill-definition.acceptance.test.ts#L5))
- **FR-006**: A CRUD REST API for skill definitions MUST be added at `/api/skill-definitions` (org-level) via `apps/lore-api/src/transport/routes/skill-definitions/` (added by this feature), mirroring the `apps/lore-api/src/transport/routes/agent-definitions/` route pattern (`agents.ts` for GET list/one/POST/PUT/DELETE, `agent-writes.ts` for admin-scope write handlers); GET requests require a read-scoped token and write operations (POST, PUT, DELETE) require admin scope; the per-repo route (`/api/repos/:o/:r/skill-definitions`) is deferred to a later version. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-4), [from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#p_92224bb0-cd6c-4554-b8c6-dbdc82373187))

- **FR-009**: `libs/shared` MUST provide domain and outbound-port logic (`project.skillDefs` under `libs/shared/src/outbound/project/`) resolving skill definitions across org defaults and per-project overrides, following the two-layer pattern (`project` row → `project_id IS NULL` org row) used by `project.agentDefs` in `libs/shared/src/outbound/project/agents/`. ### Deferred / Out of Scope (v1)

- Per-repo and per-developer skill overrides are not implemented in v1; v1 serves org-wide definitions only. The `project_id` column is reserved in `lore.skill_definitions` for a future per-repo override migration; all v1 rows use `NULL`. Individual developer customisation of org-managed skills is also deferred. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-9))
- Multi-file skills (skill directories containing assets beyond `SKILL.md`) are not supported in v1; the initial version manages one `SKILL.md` per skill. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-10))
- Vendor hook bundles (`apps/mcp-server/agent-skills/hooks/claude/`) remain baked into the gateway image and are not DB-managed in this change. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-11))
- Changes to the binary self-update flow (`lore_update` / `lore_mcp_update_available`) are out of scope; skill sync is a separate, lighter operation that does not require rebuilding the local binary. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-12))

## Success Criteria

- **SC-001**: **Skill Sync Time** — 100% of skill updates in `lore.skill_definitions` propagate to active local MCP server environments (`~/.claude/skills/<name>/SKILL.md`) within 5 minutes of saving, ready for the next Claude Code session without a manual `git pull` or re-running `scripts/install.sh`. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#k-skill-sync-time))
- **SC-002**: **Skill Presence** — 100% of enabled rows in `lore.skill_definitions` are written with a `.lore-managed` marker to the developer's `~/.claude/skills/` directory by `apps/mcp-server/src/transport/skills-sync.ts` without any manual action by the developer. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#k-skill-adoption))

## Open Questions

- **OQ-1**: Should the HTTP gateway's `/skills/*` endpoint (`apps/mcp-server/src/transport/skills-registry.ts`) for cluster agent pods serve skill definitions from `lore.skill_definitions` in the DB in a future iteration rather than from the baked-in `apps/mcp-server/agent-skills/` directory? Options: (a) serve from DB; (b) keep baked-in and add a deploy-time sync. `skills-registry.ts` is NOT changed in v1; the decision is deferred. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#scope-p-13), [from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#q_c9eec711-f3f0-4416-8e2b-cc4dfc1c1930))
- **OQ-2**: Should skills support per-repo overrides (as agent definitions do via the `/repos/[owner]/[repo]/agents` route), or are skills always org-wide? Options: (a) always org-wide (simpler); (b) per-repo overrides following the agent-definitions pattern. The `project_id` column is reserved in the table for a future migration but the policy is undecided. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#q-per-repo-overrides))
- **OQ-3**: How should local conflicts be handled if a developer manually edits a `.lore-managed` skill file at `~/.claude/skills/<name>/SKILL.md`? Options: (a) overwrite on next sync — `lore.skill_definitions` is authoritative for every `.lore-managed` directory; (b) skip the overwrite when the local file's hash diverges from the last-synced hash and log a warning instead. This also covers how the sync loop recognizes which directories it owns so it never touches a developer's hand-installed skill (answered by the `.lore-managed` marker in Constraints, but the conflict-on-edit policy itself is still open). ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#q_9a611294-5bb5-4138-b81b-d74d6ef5ba64), [from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#q_34d56c16-700e-4936-b679-38a33a2a78e8), [from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#q-managed-skill-identity))

## Constraints

- The local MCP server (`apps/mcp-server/src/transport/skills-sync.ts`, gated on `serverMode !== 'agent'` in `apps/mcp-server/src/transport/build-mcp-server.ts`) MUST fetch skill changes using `LORE_INGEST_TOKEN` without requiring any new user-facing authentication flows. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#p_a14f4062-e4ae-4ce8-a988-f2325e2d6470))
- The skill payload stored in `lore.skill_definitions` MUST map directly to the schema expected by Claude Code, with no transformation layer between DB storage and skill delivery. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#p_8793926f-314f-4abb-b019-e5d96b3c4ce9)) ([validated by SKILL_DEFINITION_COLUMNS maps projectId to the project_id column](libs/shared/src/domain/models/skill-definition.test.ts#L8))
- Agent pods MUST continue to fetch skills through the existing HTTP gateway (`apps/mcp-server/src/transport/skills-registry.ts`) under the `agent-job-egress` NetworkPolicy (public `:443` only); the dynamic skills feature MUST NOT introduce new egress requirements for agent pods. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#p_dd96d680-d52d-4ebf-894d-266cc7361bf7))
- The database migration for this feature MUST use the next free slot as `NNNN_skill_definitions.sql`; the current last migration is `0110_utopia_memory_mirror.sql` under `infra/terraform/modules/gke-mcp/lore-platform/charts/ui-helm/migrations/`. The Helm pre-upgrade hook fires on every umbrella upgrade and is idempotent (skip-if-applied), so no special handling beyond using the correct slot number is required. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#constraints-p-6), [from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#delivery-p-8))
- The skills-sync loop (`apps/mcp-server/src/transport/skills-sync.ts`) MUST NEVER remove or modify a skill directory in `~/.claude/skills/` that it did not create. The sync MUST place a sidecar ownership marker file (`~/.claude/skills/<name>/.lore-managed`, not on main) inside every directory it writes, and MUST only update or remove directories that carry that marker, leaving all others untouched; no shared manifest or external state is required. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#constraints-p-7))
- Skill changes written by the sync loop are NOT live in a running Claude Code session; they take effect only when the developer opens a new session. The 5-minute delivery KPI is defined as time from skill update to availability at the next session open, not as live injection into an already-running session. ([from plan](https://lore.gcp.re-cinq.com/repos/re-cinq/lore/plans/844e4304-7d46-463b-a4cf-3ba2202f1d4f#constraints-p-8))
