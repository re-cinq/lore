## Problem Statement

The ai-agent-subsystem supervisor POSTs the full claude stream-json run output to
the Floor as NDJSON at `POST /api/agent-events`, one line per envelope
`{"source": {task, agent, pod}, "event": <stream-json line>}`. The Floor's mapper
(`apps/floor/src/work/agent/agent-events.ts`) projects only the terminal `result`
line into a `pipeline.llm_calls` cost row and skips every other line silently.

The raw body is not discarded. When this feature shipped, the route
(`apps/floor/src/transport/http/routes/agent-events.ts`) archived the redacted
NDJSON to GCS fire-and-forget — write-only, keyed by timestamp rather than by
run, with no cursor and no live tail — so this feature added a queryable
projection alongside that archive rather than rescuing discarded data.
_(Amended 2026-08-11, #1148:)_ the GCS archive is retired; the full redacted
stream now lives in `pipeline.agent_run_turns`
(`specs/turn-level-transcript-store`), which is keyed by run, correlated, and
readable over HTTP.

The observable result today is that a developer watching an assembly line has a
task row, a set of node rows, and a PR link — but no view of what the agent is
actually doing inside a node while it runs. Every live view in the product is a
4–15 second `setInterval` poll, which cannot render a per-tool-call stream at a
useful granularity.

## Goals & Non-Goals

- The first cut delivers persistence, live transport, history, and the run visualization behind session-authenticated web-ui proxies.
- There is deliberately no `node_status` event type; node state is seeded from `pipeline.assembly_line_nodes` and derived from per-node `init` / `result` events, because a second source of truth for node status would drift against the table the walk actually writes.
- Retention of the raw stream is out of scope; this feature owns only the `pipeline.agent_run_events` prune. (The GCS raw-NDJSON archive this line once deferred to was retired 2026-08-11 in favor of the `pipeline.agent_run_turns` transcript and its own 30-day prune, #1148.)
- Cost accounting is unchanged in the sense that this feature introduces no new cost semantics, no new cost schema, and no change to which line produces a `pipeline.llm_calls` row.

## Retired Requirements (Background)

- FR5.8 _(retired 2026-09-09)_: the 10-second `router.refresh()` of the server-rendered half while a run was live. Removed: the header, the node rows and the task events now change in place from the multiplexed stream (FR7.8–FR7.10). The retired statement read:
  - FR5.8. _(added 2026-09-02)_ A live run's page keeps up with the SERVER-RENDERED half of itself. The SSE stream carries agent events, deliberately not node state (ADR-037; node state seeds from `pipeline.station_runs`), so the header status, the panel's seed node rows and a recorded outcome only changed on a manual reload. While the run is non-terminal the page re-runs its server component on a 10s cadence (`router.refresh()` — client state, the stream and the selection survive it); a terminal run refreshes nothing, because its snapshot is the truth and an idle page must not poll forever.
- FR4.4i, FR4.6b–d _(retired 2026-09-09)_: the run Timeline card (lifecycle ticks on a wall-clock rail) and the replay scrubber (terminal-run fold to a cursor, the pure slider control, and tick-to-cursor seeking). The retired statements read:
  - FR4.4i. Each lifecycle tick is placed at its wall-clock fraction of the run's span, whose right bound is the live run's moving `now`, and is coloured by event type, so a node whose latest tick lags far behind the now edge reads as stalled; a run with no ticks renders an explicit empty state rather than a bare rail, and the whole strip renders as a collapsible card titled Timeline.
  - FR4.6b. The replay scrubber renders only for a terminal run and folds that run's persisted history through the same reducer to a chosen cursor, so the graph, transcript, heatmap, and timeline all render the state as of that event; a live run keeps streaming and shows no scrubber, and a Back to live control clears the cursor to restore the final state. The reducer is therefore replayable-from-zero — folding from the all-idle base to cursor N, advancing past it, and rewinding to N yields byte-identical state — which is the only reason a node's status and iteration rewind rather than only advance.   - FR4.6c.
