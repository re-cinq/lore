# Feature Specification: Implementation Loop

| Field     | Value                                                                    |
|-----------|--------------------------------------------------------------------------|
| Feature   | Implementation Loop                                                      |
| Status    | In Progress                                                              |
| Created   | 2026-08-24                                                               |
| Owner     | Platform Engineering                                                     |
| Builds on | [specs/github-issue-dispatch](../github-issue-dispatch/spec.md)          |

Lore reacts but never initiates. A human labels an issue, one task runs, one PR opens, and the factory goes quiet until the next human gesture. This feature gives a repo a backlog and a loop that works it: pick the highest-priority open issue, implement it test-first, open a PR, wait until that PR is green with no outstanding review comments, then pick the next one. It never merges — a human still does that, whenever they like.

## Problem Statement

Today's path from issue to PR is a single-shot reaction. `issuesLabeled` in `apps/floor/src/jobs/github.ts` fires only on `action === "labeled"`, compares the added label against the repo's `dispatch_label`, and mints one `pipeline.tasks` row. The Floor worker claims it, `AssemblyLineStationBackend.launch` starts the `implementation` line, a PR opens, and the chain terminates there.

Three things are missing.

**There is no backlog.** The only ordering anywhere is the binary `priority` column on `pipeline.tasks` (`normal` | `immediate`) read by `claimNextPending` in `libs/shared/src/project/tasks/task-queue-pg.ts`. The webhook dispatch path never sets it, so every issue-dispatched task lands at `normal` and is claimed strictly in `created_at` order. Nothing in the repo expresses "this issue matters more than that one" — the label taxonomy in `docs/using-lore/developer.md` is purely routing (`lore`, `lore:implementation`, `lore:review`, `lore:runbook`) with no severity dimension.

**There is no re-arm.** When a run finishes, nothing looks for the next piece of work. Every ticket needs its own human label gesture to enter the system.

**There is no visibility into what is queued.** The Features tab at `apps/web-ui/src/app/repos/[owner]/[repo]/features/` shows planning work; nothing shows implementation work in flight or waiting.

A fourth gap sits underneath the "wait until the PR has no outstanding comments" requirement: the review round-trip in `apps/floor/src/jobs/review/code-review.ts` posts replies through `postReplyFromNode` but never resolves the review thread. GitHub exposes thread resolution only over GraphQL, and this repository contains no GraphQL client — `grep -rni graphql` over every `src/` returns zero hits. Without resolution there is no durable signal that a comment has been dealt with, so "no outstanding comments" is not currently computable.

## FR1 — Priority taxonomy and eligibility

- The repo carries four new labels: `priority:high`, `priority:medium`, `priority:low`, and `lore:blocked`. ([validated by seeds the priority taxonomy](../../apps/floor/src/jobs/task/worker.onboard.test.ts#L332))
- An issue is eligible for the queue when it is open, carries exactly one `priority:*` label, does not carry `lore:blocked`, and has no open Lore-authored PR already referencing it. ([validated by skips a closed issue](../../libs/shared/src/backlog/select-next-issue.test.ts#L71), [validated by skips lore:blocked](../../libs/shared/src/backlog/select-next-issue.test.ts#L80), [validated by ignores unrelated labels](../../libs/shared/src/backlog/select-next-issue.test.ts#L121))
- Queue order is `priority:high` before `priority:medium` before `priority:low`; ties are broken by oldest `created_at` first. ([validated by picks priority:high first](../../libs/shared/src/backlog/select-next-issue.test.ts#L30), [validated by picks priority:medium next](../../libs/shared/src/backlog/select-next-issue.test.ts#L40), [validated by breaks a tie by oldest](../../libs/shared/src/backlog/select-next-issue.test.ts#L49), [validated by undated sorts last](../../libs/shared/src/backlog/select-next-issue.test.ts#L108))
- An issue carrying no `priority:*` label is never picked. Applying a priority label is the opt-in; no second dispatch label is required. ([validated by no priority label returns null](../../libs/shared/src/backlog/select-next-issue.test.ts#L21))
- An issue carrying more than one `priority:*` label is treated as ineligible rather than silently resolved to the highest, so the ambiguity surfaces to a human instead of being guessed at. ([validated by multiple priority labels ineligible](../../libs/shared/src/backlog/select-next-issue.test.ts#L89), [validated by all-ineligible returns null](../../libs/shared/src/backlog/select-next-issue.test.ts#L98))
- The selection logic is a pure function over a list of issue records, with no I/O, so ordering is testable without GitHub. ([validated by empty backlog returns null](../../libs/shared/src/backlog/select-next-issue.test.ts#L17))

## FR2 — The loop is a driver, not a cyclic assembly line

- Each assembly run handles exactly one ticket. The loop lives in a Floor handler following the shape of the detection fan-out in `apps/floor/src/jobs/detect/fan-out.ts` — with one refinement over the original sketch: it mints an `implementation-loop` **task** rather than a bare run, so the whole existing machinery (worker claim, line launch, agent CRs, the watcher's PR-open, the pr_url stamp) rides along unchanged. The task type sits on the `implementation` trust tier. ([validated by top pick mints a task](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L44), [validated by allowed at implementation trust](../../libs/shared/src/pipeline-tasks.trust.test.ts#L66), [validated by refused at tests trust](../../libs/shared/src/pipeline-tasks.trust.test.ts#L78))
- The loop is not expressed as a back-edge in the line's YAML. `libs/assembly-lines/src/loader.ts` rejects an unbounded cycle unless a human station gates it, so a cyclic definition would require an `iteration_max` — capping a repo's backlog at a literal integer — and would require a new node type, which costs changes in the loader enum, `PRODUCIBLE_OUTCOMES`, the station runner, the station map, `scripts/task-types.yaml`, the web-ui type mirror, and two drift checks. ([validated by back-edge needs iteration_max](../../libs/assembly-lines/src/loader.test.ts#L255))
- Only one run per repo is in flight at a time. Serialisation reuses the existing unique index on `pipeline.assembly_runs (repo, subject_key)` for open rows: an implementation-loop task's run declares the constant `backlog` subject (the repo is the index's other half, so the key carries no repo — exactly as `reviewSubject` carries none), and `PgAssemblyRuns.start` returns the id of the in-flight run instead of creating a second one. The mint-to-run gap is covered by the picked issue's active task. ([validated by backlog subject on the run](../../apps/floor/src/jobs/assembly-run/assembly-run-station-backend.test.ts#L127), [validated by constant backlog key](../../libs/shared/src/project/assembly-runs/subject-keys.test.ts#L59), [validated by open run skips the repo](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L96), [validated by active task skips the pick](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L104))
- The driver runs on a cron tick as a safety net and is also re-armed from the run's terminal hook — `finishLine`'s winning finisher emits a repo-scoped tick event — so there is no scheduling gap between one ticket finishing and the next starting. ([validated by completed run re-arms](../../apps/floor/src/jobs/backlog/loop-run-closed.test.ts#L65), [validated by repo-scoped tick](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L120), [validated by a green PR re-arms through the real walk](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L121))
- On each invocation for a repo the driver skips when the repo's toggle is off, skips when an open run already holds the repo's subject key, and otherwise walks the queue in pick order PAST tickets an earlier task still guards — completed-awaiting-merge, mostly — minting the task for the first unguarded ticket, carrying the issue number and URL. Returning on a guarded HEAD instead of walking past it froze the whole backlog behind one unmerged PR twice (27h on 2026-08-30, overnight on 2026-09-02), and the FR10 next-up list already filters guarded tickets out, so the first ticket it shows must be the one the driver picks; serialisation is the open-run subject check's job, not this walk's. When eligible tickets exist but every one is guarded, the driver SAYS so — one log line naming the guarded tickets — because a backlog that exists but cannot be picked is indistinguishable from a dead loop when it is silent. ([validated by toggle off does nothing](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L88), [validated by issue number on the task](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L44), [validated by one broken repo never stops the sweep](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L137), [validated by skips a head whose task is completed-awaiting-merge and picks the next eligible ticket](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L254), [validated by says why when every eligible ticket is guarded, instead of exiting silently](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L268), [validated by stays silent about an empty backlog — a normal state, not a stall](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L290))
- When no issue is eligible the driver does nothing and leaves no run behind. An empty backlog is a normal state, not a failure. ([validated by empty backlog no-op](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L112))
- The ticket description carries the issue TITLE AND BODY *(amended 2026-09-03, #1745)*, because the DoD node defines done against it and its scope-fidelity contract asks the agent to quote the ticket's central claim — a claim a one-line title does not carry: bowman-ui #11's DoD redefined exactly such a title-only ticket into a different problem. A bodyless or blank-bodied issue stays title-only, and a body past 16,000 characters is cut there with an explicit `[issue body truncated]` marker, since issue bodies are unbounded (a generated link report ran ~40KB) and the description lands in every loop pod's prompt; the octokit adapter surfaces the body on `IssueRef` for it, omitting GitHub's `null`. ([validated by body under the title](../../apps/floor/src/jobs/backlog/ticket-description.test.ts#L5), [minted through the picker](../../apps/floor/src/jobs/backlog/implementation-loop.test.ts#L68), [no body stays title-only](../../apps/floor/src/jobs/backlog/ticket-description.test.ts#L16), [blank body stays title-only](../../apps/floor/src/jobs/backlog/ticket-description.test.ts#L22), [40KB body capped and marked](../../apps/floor/src/jobs/backlog/ticket-description.test.ts#L31), [at-cap body unmarked](../../apps/floor/src/jobs/backlog/ticket-description.test.ts#L43), [adapter carries the body](../../libs/shared/src/project/lib/platform-github.test.ts#L158))

## FR3 — The assembly line definition

- The `implementation-loop` definition is top-down: acceptance tests bound the work before any of it is done, one red-green-refactor round runs per pod visit, and red CI is repaired rather than escalated. Its nodes are `dod`, `open-pr`, `tdd-round`, `validate`, `ready-for-review`, `await-pr` (human station of type `pr_review`), `fix-ci`, `retrospective` and `done`; the happy path runs them in that order. ([validated by `implementation-loop-line.test.ts:33`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L33), [`implementation-loop-line.test.ts:158`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L158), [`implementation-loop-acceptance.test.ts:61`](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L61), [`implementation-loop-acceptance.test.ts:121`](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L121))
- Every agent node carries an explicit `station_ref`. An agent node's Station otherwise inherits the LINE's task type, and no Station named `implementation-loop` exists — which is exactly how the first live run died. ([validated by `implementation-loop-line.test.ts:44`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L44))
- `open-pr` runs the `push-only` recipe, the one `prompt_ref` the Floor stamps `args.pr_url`/`pr_number` for. `await-pr`'s `route: "{args.pr_url}"` reads what that stamp writes, so any other recipe there would park the run on a route that never resolves. ([validated by `implementation-loop-line.test.ts:59`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L59))
- `tdd-round` loops on `changes_requested` — "round green, work remains" — with `iteration_max: 12`, and leaves on `success`. Twelve rounds on one ticket means it was mis-sized and its acceptance tests should have been split, so the budget failing IS the diagnosis rather than an accident. ([validated by `implementation-loop-line.test.ts:67`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L67), [`implementation-loop-line.test.ts:116`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L116), [`implementation-loop-acceptance.test.ts:80`](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L80))
- `tdd-round` has exactly ONE self-edge. `iteration_max` counters key on `${from}->${to}` and not on the outcome, so a second self-edge would share the first's budget and a `failed` round would be judged against a budget it never spent. `failed` therefore routes to the retrospective with no retry available. ([validated by `implementation-loop-line.test.ts:77`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L77))
- Red CI routes `await-pr` to `fix-ci` and back to the wait, rather than blocking the ticket. The cycle touches a human station, so the loader demands no `iteration_max` — but one is declared anyway and the runtime enforces it, because a permanently red PR would otherwise ping-pong forever. ([validated by `implementation-loop-line.test.ts:86`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L86), [`implementation-loop-line.test.ts:91`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L91), [`implementation-loop-line.test.ts:137`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L137), [`implementation-loop-acceptance.test.ts:110`](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L110))
- Unresolved review threads route to a human instead, because no build fix answers a reviewer. ([validated by `implementation-loop-line.test.ts:97`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L97))
- `dod` retries itself once on `failed`, and routes `changes_requested` — "this ticket cannot be expressed as acceptance tests" — straight to the retrospective. That is a scoping verdict, not a failure: a retry cannot make an unclear ticket clear, only a human can. ([validated by `implementation-loop-line.test.ts:101`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L101), [`implementation-loop-acceptance.test.ts:150`](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L150))
- A trivial or mechanical ticket — a rename, a deletion, a documentation update — has no behaviour to write tests for first; tests would exercise the compiler rather than a behaviour. `dod` signals this with `no_new_test`, routing to `open-pr` on the same path as `success`; `tdd-round` reads `.lore/dod.md`, sees `Strategy: no-new-test`, and implements the change directly without a red bar. `changes_requested` remains the verdict for a ticket that is unclear or ambiguous, not for one that is clear but mechanical. The `acceptance-dod` recipe names `no_new_test` as a valid outcome so the agent knows when to return it, and the line YAML carries the edge so the run is not failed by `selectEdge` finding no match. ([validated by routes no_new_test to open-pr](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L171), [validated by names no_new_test in the recipe](../../libs/shared/src/task-types/task-types-config.test.ts#L188))
- A `validate` failure routes back to a round on its OWN budget, so lint breakage cannot eat the round budget. ([validated by `implementation-loop-line.test.ts:109`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L109))

- A revisit is numbered past the node's HIGHEST recorded iteration, not per edge: `(node, iteration)` is the row identity, so numbering per edge reissued an iteration the idempotent launch then found already finished, and the run sat `running` with no open node. A node sent back by a failure is TOLD what failed — the failing step's name and its own output, with validation summaries lifted from the `Lore-Validation-Failed` extras onto `failureDetail`, and the exhausted budget as the closing clause rather than the whole story. Without it the loop could not converge and did not: three live runs exhausted `iteration_max` being handed a byte-identical prompt (2026-08-26). ([validated by `transition.test.ts:404`](../../libs/assembly-lines/src/transition.test.ts#L404), [`transition.test.ts:431`](../../libs/assembly-lines/src/transition.test.ts#L431), [`node-outcome.test.ts:296`](../../libs/assembly-lines/src/node-outcome.test.ts#L296), [`transition.test.ts:483`](../../libs/assembly-lines/src/transition.test.ts#L483), [`transition.test.ts:500`](../../libs/assembly-lines/src/transition.test.ts#L500), [`implementation-loop-line.test.ts:101`](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L101), [`implementation-loop-acceptance.test.ts:150`](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L150))

- A `validate` that no cluster ever claimed is NOT a `validate` failure and buys
  no retry. The back-edge exists so a real lint or typecheck failure can be
  fixed by the node that caused it; when the station never ran, re-running
  `implement` cannot change whether a cluster exists to take the next visit.
  Between 2026-08-28 and 2026-08-29 it did exactly that on five consecutive
  tickets — `implement` succeeded on the satellite in ~25 minutes, `validate`
  needed `node:validate`, the only cluster offering it was paused, the reaper
  failed the visit as retryable `infra`, and the loop spent the budget on a
  second 25-minute `implement` before waiting out another 30-minute
  queue-timeout and blaming the exhausted edge. Each ticket cost about two hours
  and two full implementations to reach a `lore:blocked` label, and the driver
  re-armed straight into the next one (#1648, #1650, #1647, #1634, #1629). The
  queue-timeout class is `unclaimed` and permanent (6-dark-factory FR6.56), so
  the run now fails once, naming the cluster that was switched off. ([validated by fails the run instead of re-launching the round](../../libs/assembly-lines/src/transition.test.ts#L545), [validated by reports the paused cluster as the cause, not the spent retry budget](../../libs/assembly-lines/src/transition.test.ts#L551), [`transition.test.ts:565`](../../libs/assembly-lines/src/transition.test.ts#L565), [validated by still routes a genuine validate failure back to implement](../../libs/assembly-lines/src/transition.test.ts#L551), [validated by fails the run once and never re-dispatches implement](../../apps/floor/src/jobs/assembly-run/assembly-run-reaper.test.ts#L1254))
- A node dispatched after a failure is TOLD what failed. The retried agent
  receives the failing step's name and its own output appended to the prompt,
  under a heading naming it as the previous step's failure. Without it the
  loop could not converge and never did: `implement` succeeded, `validate`
  failed, and the retry was dispatched with a byte-identical prompt — three
  live runs exhausted `iteration_max` this way (2026-08-26). `priorOutcomeOf`
  cannot supply this, because it answers for ONE node and so told `implement`
  about its own last visit, which was `success` every time; the feedback comes
  from the most recently recorded visit instead, whichever node produced it.
  A verdict (`changes_requested`) is not a failure and carries no such block. ([validated by `launch-spec.test.ts:15`](../../apps/floor/src/jobs/assembly-run/launch-spec.test.ts#L18), [`launch-spec.test.ts:32`](../../apps/floor/src/jobs/assembly-run/launch-spec.test.ts#L35), [`launch-spec.test.ts:41`](../../apps/floor/src/jobs/assembly-run/launch-spec.test.ts#L44), [`launch-spec.test.ts:50`](../../apps/floor/src/jobs/assembly-run/launch-spec.test.ts#L53), [`launch-spec.test.ts:55`](../../apps/floor/src/jobs/assembly-run/launch-spec.test.ts#L58), [`launch-spec.test.ts:66`](../../apps/floor/src/jobs/assembly-run/launch-spec.test.ts#L69), [`launch-spec.test.ts:70`](../../apps/floor/src/jobs/assembly-run/launch-spec.test.ts#L73), [`launch-spec.test.ts:81`](../../apps/floor/src/jobs/assembly-run/launch-spec.test.ts#L84), [`advance.test.ts:590`](../../apps/floor/src/jobs/assembly-run/advance.test.ts#L592))
- The `validate` station reports the failing commands' OWN OUTPUT, not just
  their names. `Lore-Validation-Failed: "lint,build"` says where to look; the
  compiler errors say what to fix, and the agent sent back to fix them is the
  one reading it. The output is bounded twice — per command by `runValidation`,
  then across all of them — because it rides an Agent CR's status, where an
  oversized object has already lost a run. ([validated by `validate-handler.test.ts:75`](../../libs/assembly-lines/src/validate-handler.test.ts#L75), [`node-outcome.test.ts:77`](../../libs/assembly-lines/src/node-outcome.test.ts#L77), [`validate-handler.test.ts:86`](../../libs/assembly-lines/src/validate-handler.test.ts#L86))
- `await-pr` resuming with `success` means the PR is ready and the ticket is complete; resuming with `changes_requested` means the ticket is blocked. Both route to `retrospective` so the run always closes through the same exit. ([validated by one exit for both](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L67))
- `await-pr` declares `route: "{args.pr_url}"`, satisfying the loader's requirement that a human station carry a route built only from `{args.*}` placeholders. ([validated by pr_review park](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L33))
- The definition introduces no new node type. `implement` is an ordinary `agent` node carrying an explicit `station_ref: implementation-tdd` — an agent node's Station otherwise inherits the LINE's task type, and no Station named `implementation-loop` exists, which is exactly how the first live run died; `validate`, `push` and `retrospective` reuse the existing station recipes unchanged. ([validated by implementation-tdd recipe](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L44), [validated by explicit station_ref](../../libs/assembly-lines/src/implementation-loop-line.test.ts#L116))

## FR4 — Waiting on the pull request

- A node of type `pr_review` parks: `apps/floor/src/jobs/assembly-run/advance.ts` mints the station run row but dispatches no Agent CR, and the reaper classifies it as `wait` so it is never timed out. The run sits at `await-pr` indefinitely and the graph shows whose move it is. ([validated by human node never times out](../../apps/floor/src/jobs/assembly-run/assembly-run-reaper.test.ts#L196), [validated by the walk parks await-pr with no CR dispatched](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L61))
- A polling station job evaluates every open `implementation-loop` run parked at `await-pr` and reports the verdict through the existing `parkedHumanNode` and `reportToParkedNode` helpers, which insert an `assembly_run.resume` event — the same mechanism `resumeDecomposition` already uses to unpark a feature-planning line on a merged spec PR. A run not parked at a `pr_review` node, or parked without a `pr_number` in its args, is skipped, and one PR read failing never stops the sweep. ([validated by resumes a parked run](../../apps/stations/src/stations/pr-ready-check/pr-ready-check.test.ts#L59), [validated by not-parked skipped](../../apps/stations/src/stations/pr-ready-check/pr-ready-check.test.ts#L132), [validated by no pr_number skipped](../../apps/stations/src/stations/pr-ready-check/pr-ready-check.test.ts#L145), [validated by one error never stops the sweep](../../apps/stations/src/stations/pr-ready-check/pr-ready-check.test.ts#L163))
- A PR is ready when its CI conclusion is `success` and it has zero review threads that are unresolved and not outdated. Both conditions must hold; a CI conclusion of `none` counts as green only on a repo with no CI history (FR13), so a repo with no checks cannot wedge its loop. ([validated by ready on green](../../apps/stations/src/stations/pr-ready-check/decide-ready.test.ts#L40), [validated by none counts as green](../../apps/stations/src/stations/pr-ready-check/decide-ready.test.ts#L51), [validated by none still blocks on threads](../../apps/stations/src/stations/pr-ready-check/decide-ready.test.ts#L131))
- A PR whose CI conclusion is `pending` produces no verdict; the job re-evaluates on its next tick. ([validated by pending waits](../../apps/stations/src/stations/pr-ready-check/decide-ready.test.ts#L14), [validated by pending reports nothing](../../apps/stations/src/stations/pr-ready-check/pr-ready-check.test.ts#L86))
- The two blocking reasons resume with DIFFERENT outcomes, because only `outcome` routes — `selectEdge` matches on it alone and the `reason` reaches the run's args steering nothing. Red CI resumes `changes_requested`, which the line routes to `fix-ci`; unresolved threads resume `failed`, which routes to a human. Collapsing them onto one outcome would have made the line unable to tell a build it can repair from a conversation it cannot. ([validated by `decide-ready.test.ts:107`](../../apps/stations/src/stations/pr-ready-check/decide-ready.test.ts#L107), [`decide-ready.test.ts:118`](../../apps/stations/src/stations/pr-ready-check/decide-ready.test.ts#L118), [`implementation-loop-acceptance.test.ts:136`](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L136), [`loop-run-closed.test.ts:75`](../../apps/floor/src/jobs/backlog/loop-run-closed.test.ts#L75), [`decide-ready.test.ts:25`](../../apps/stations/src/stations/pr-ready-check/decide-ready.test.ts#L25), [`decide-ready.test.ts:87`](../../apps/stations/src/stations/pr-ready-check/decide-ready.test.ts#L87), [`pr-ready-check.test.ts:73`](../../apps/stations/src/stations/pr-ready-check/pr-ready-check.test.ts#L73), [`pr-ready-check.test.ts:119`](../../apps/stations/src/stations/pr-ready-check/pr-ready-check.test.ts#L119))

## FR6 — Test-first implementation prompt

- Four recipes drive the line's agent nodes — `acceptance-dod`, `tdd-round`, `fix-ci` and `pr-ready`. The existing `implementation` recipe is left untouched, because the existing `implementation` line still uses it. Each declares the `tdd-loop` agent skill rather than restating the red-green-refactor contract inline, so the contract has one copy and the recipes stay about their own step. `acceptance-dod` also declares `legacy-characterize`, for the strategy that needs it.
- `acceptance-dod` writes the RED acceptance tests that define done, taking a spec's UN-LINKED testable statements as its work list where the ticket names one, and writes no production code at all. ## FR8 — Blocked tickets never stall the loop

- When a run ends blocked or errored, the driver applies `lore:blocked` to the issue and comments on it explaining why, naming the failing condition and linking the run. A blocked ticket is recognised by its `pr_review` node having resumed anything but `success` — `failed` for review threads the address round-trip did not clear, `changes_requested` for a build still red after the repair attempts were spent. A REPAIRED build never reaches this hook: `fix-ci` success routes back to the wait, which opens a new `pr_review` row and parks the run again, so a CLOSED run resuming `changes_requested` is one where the repair gave up. Blocking only on `failed` let that ticket re-arm into a fresh run whose `await-pr` → `fix-ci` counter starts at zero, so a build that cannot be reproduced locally would cycle across runs without bound — `iteration_max` bounds one run and nothing bounded the re-arm. An errored ticket is recognised by the run's failure outcome; any other blueprint's run is ignored. ([validated by blocked on failed](../../apps/floor/src/jobs/backlog/loop-run-closed.test.ts#L75), [validated by failed run blocks](../../apps/floor/src/jobs/backlog/loop-run-closed.test.ts#L102), [validated by other blueprints ignored](../../apps/floor/src/jobs/backlog/loop-run-closed.test.ts#L111), [validated by a not-ready PR blocks and still re-arms](../../apps/floor/src/jobs/assembly-run/implementation-loop-acceptance.test.ts#L80))

## FR13 — "No checks" is two different answers

- `ciConclusion` returns `none` both for a repo that runs no checks AND for a head sha whose checks have not registered yet, and those readings are opposites. Treating `none` as green — which is right for the first, so a repo without CI cannot wedge its loop — resumed the line on an UNVERIFIED build in the window between a push and GitHub creating the first check run. The two are told apart by whether the repo runs checks at all, asked of its default branch: a repo fact, not a clock, so the verdict stays a pure function with no timers in it. ## Alternatives Rejected

**A cyclic assembly line with a back-edge from `done` to a pick node.** The loader refuses an unbounded cycle unless a human station gates it, so this needs an `iteration_max`, which caps a repo's backlog at a literal integer written into a YAML file. It also needs a new node type for the pick step, touching the loader enum, the outcome table, the station runner and its map, the task-types recipe file, the web-ui type mirror and two drift checks. A driver achieves the same behaviour with no new node types and no cap.

**A bespoke address node inside this line.** The `code-review-reply` line already implements exactly this: it takes a triaged comment, commits the fix on the PR branch, and posts the reply. Duplicating it would create a second implementation of the same behaviour that would drift from the first.

**Putting the toggle inside `dark_factory`.** That block's fields are privileged because they confer merge authority, and touching any of them requires an approval PR labelled by a CODEOWNER. This loop never merges, so binding it to that ceremony would impose a cost with no matching risk.

**Running several tickets per repo concurrently.** "Pick the top most important ticket" describes a serial queue. Concurrency would require per-issue claim mechanics so two runs never grab the same ticket, and would make the "current ticket" section of the UI a list. It is deferred until a repo demonstrably starves.

**Deriving readiness from a Lore-side tally of addressed comments.** Lore would then disagree with GitHub about whether a comment had been dealt with, and a human resolving a thread by hand would be invisible. Reading GitHub's own resolved flag keeps one source of truth, at the cost of adding a GraphQL client.

## Out of Scope

- Merging. A human merges every PR this loop produces; the loop has no merge authority and requests none.
- Cross-repo scheduling or a global priority queue spanning repos. Each repo's loop is independent.
- Concurrency above one ticket per repo.
- Commit-status support in the green check; the Checks API is the only source.
- Automatic priority assignment. A human decides what `priority:high` means.
- Cancelling an in-flight run when the toggle is switched off.
