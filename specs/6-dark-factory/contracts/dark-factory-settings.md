# Contract: Dark Factory settings API

Endpoints for reading and mutating the per-repo `settings.dark_factory` block. Tiered authorization per FR3.9.

## Endpoints

### `GET /api/repos/:owner/:repo/settings/dark-factory`

Read current settings. Requires `read` scope.

**Response 200:**

```json
{
  "enabled": false,
  "create_issue": "on_gate",
  "auto_merge": {
    "paths": ["specs/**", "adrs/**", "*.md", "CLAUDE.md", ".claude/**"],
    "min_trust": "docs",
    "require_green_ci": true,
    "require_bot_approval": true
  },
  "review": "trust_based",
  "notify": ["escalation"]
}
```

**Response 404:** repo not onboarded.

### `PUT /api/repos/:owner/:repo/settings/dark-factory`

Mutate settings. Body MUST be a partial patch (only fields to change).

Requires `admin` scope. If the patch touches a **two-key field** (per data-model.md):

- Header `X-Lore-Approval-PR: <owner>/<repo>#<number>` MUST be present.
- The referenced PR MUST be `merged: false`, have label `dark-factory-approval`, and the label MUST have been applied by a member listed in the affected repo's `CLAUDE.md` CODEOWNERS scope.
- Validation occurs server-side; failure returns 403.

**Request body:**

```json
{
  "enabled": true,
  "auto_merge": {
    "paths": ["specs/**", "*.md", "runbooks/**"]
  }
}
```

**Response 200:**

```json
{
  "ok": true,
  "audit_log_id": "audit_evt_abc",
  "applied": { "enabled": true, "auto_merge.paths": [...] }
}
```

**Response 400:** Zod validation error (returns issues array).

**Response 403:**
- `error: "two_key_required"` with `field_path` indicating which key triggered.
- `error: "codeowners_check_failed"` with detail (label missing, applier not in CODEOWNERS, PR not found).

**Response 401:** missing or invalid scope.

## Two-key fields

| Field path | Why two-key |
|---|---|
| `enabled` | Master switch — enabling grants the bot merge authority |
| `auto_merge.paths` | Expanding allowlist directly increases blast radius |
| `auto_merge.require_green_ci` (only when set to `false`) | Disabling CI gate is a downgrade |
| `auto_merge.require_bot_approval` (only when set to `false`) | Disabling bot review gate is a downgrade |

All other sub-fields require admin scope only.

## Audit log entry

Every successful PUT writes a `dark_factory_setting_changed` audit_log entry (schema in data-model.md).

## CODEOWNERS approval ceremony

The "approval PR" referenced by `X-Lore-Approval-PR` is a PR against any path that:

1. Modifies a settings file under `lore-settings/<repo>.yaml` (or an equivalent settings-edit PR generated by the web-ui), AND
2. Has been labeled `dark-factory-approval` by a CODEOWNERS member of the affected repo's `CLAUDE.md`, AND
3. Is currently open (not merged or closed).

Implementation note: an unmerged PR is intentional — the PR is the ceremony, not the change. Once the settings PUT succeeds, the PR can be merged (or closed) separately as a record. The web-ui settings editor can automate creating + auto-labeling this PR if the actor has both admin scope and CODEOWNERS membership; otherwise it's a manual gh-cli step.

## Failure modes

| Failure | Behavior |
|---|---|
| GitHub API down at validation time | 503 with `Retry-After: 30` |
| CODEOWNERS file unparseable | 500 with audit_log entry; settings unchanged |
| Concurrent two-key changes (race) | Last-writer-wins; both get 200; both audit entries present |

## Per-task overrides

Per-task `dark_factory_overrides` are set at task creation via the existing `POST /api/tasks` endpoint:

```json
{
  "task_type": "general",
  "description": "...",
  "target_repo": "owner/repo",
  "dark_factory_overrides": {
    "human_review": "required",
    "with_issue": true,
    "notify_on_completion": true
  }
}
```

No special AuthZ — the per-task overrides only *strengthen* gates (force human review, force Issue creation), they cannot weaken them.
