# Feature Specification: Planning a Feature Together

| Field          | Value                                       |
|----------------|---------------------------------------------|
| Feature        | Planning a Feature Together                 |
| Branch         | 7-feature-planning                          |
| Status         | In Progress                             |
| Created        | 2026-06-17                                  |
| Owner          | Platform Engineering                        |

A feature is planned as a plan people and the planning agent write together in one live document, in a fixed template, until someone approves it; approval hands the plan to the spec PR and to decomposition on the same assembly line.

## Problem Statement

Planning used to be a wizard over `lore.features`: one author typed direction per
section, the agent regenerated its whole gap analysis every round, and nobody else
could work on the draft. The people who own a change — product, engineering, the
team that will run it — could not write it together, and every round threw away
what the last one had settled.

## How a plan moves

A plan is created from a title, a template and what the author already knows, and
its planning line starts at once. The agent drafts into the live plan while people
read and write it (ADR-047). A section's **Refine** sends that section back to the
agent, whose answer comes back as a proposal someone accepts. Approval ends the
plan: the same line analyses which specs it changes, writes and pushes them, waits
for the spec PR to merge, decomposes the merged spec into stories and tasks, and
files them.

### FR-18: The planning line drives the plan

One `feature-planning` assembly line carries a plan from its first draft to its
spec-tasks. Its agent writes into the live plan through lore-api, its `author`
node parks while people write, and approval moves the same line on to the spec
PR and decomposition.

- Creating a plan starts its line: a `feature-planning` task whose brief is the plan as it stands plus what the author already knows, whose run is keyed `plan:<id>` so one plan has one line in flight, and whose args carry the repo and the plan's title ([validated by](../../apps/lore-api/src/work/plans/planning-line.test.ts#L46), [validated by](../../apps/lore-api/src/work/plans/plan-briefs.test.ts#L10), [validated by](../../libs/shared/src/outbound/project/assembly-runs/subject-keys.test.ts#L12), [validated by](../../libs/shared/src/outbound/project/assembly-runs/subject-keys.test.ts#L38), [validated by](../../apps/lore-api/src/integration-tests/plan-routes.test.ts#L171)).

### FR-3: Gap-Closing Result
