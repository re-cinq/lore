# Five-pass pull request review

**Proposed for the code-review and code-review-recheck assembly lines.** A PR author sees one evolving GitHub comment and one final verdict for the reviewed commit. Lore first establishes what the implementation does and what the tests prove. It then compares those independent accounts with human intent, challenges the tests, and evaluates the product impact.

The earlier two-phase replay caught a missing refusal test and an unrelated status change, but missed a confirmed parser defect and produced unsupported blockers. Use those cases for calibration. The five-pass design still needs its own full replay and shadow pilot. [Historical results and example comments](../docs/building-lore/two-phase-review-replay-2026-11-19.md)

## What each reviewer sees and produces

| Pass | Inputs | Contribution to the review |
| --- | --- | --- |
| **1. Explain the code** | Implementation and configuration changes, plus relevant unchanged callers, registrations, and side effects. Exclude tests, Markdown, tickets, PR text, comments, and prior reviews. | Post exactly two sentences. Describe what changes for a user or maintainer, then the important condition, exception, or preserved behavior. Account for independent changes in a mixed diff. A neutral description gives the author a chance to correct a misunderstanding. |
| **2. Explain the tests** | Changed and relevant existing tests, their fixtures, doubles, and assertions. Exclude implementation bodies, Markdown, ticket and PR context, and the opening comment. | Describe what the assertions establish. Name the test behind each material claim and say where a mock limits the conclusion. If the tests are unchanged, describe existing evidence where relevant. A test that checks a call to a guard establishes less than a test that observes a refusal and the absence of a protected write. |
| **3. Compare the readings with intent** | The recorded explanations from 1 and 2, the linked issue and its comments, and the PR title, body, conversation, inline threads and replies. Exclude Lore’s review summary from the evidence of human intent. | Explain where implementation, tests, and agreed scope align. For a material discrepancy, cite the conflicting statements and verify the relevant path or assertion before raising a finding. An omission in a two-sentence explanation is a reason to check. If the issue and PR disagree, look for an explicit scope decision in the discussion. Surface unresolved decisions as questions for the author. |
| **4. Challenge the tests independently** | Implementation, consumers, tests and fixtures at the reviewed revision. Withhold issue and PR context, specs, GitHub comments and all other pass outputs. | Ask “What materially wrong behavior could still pass?” Follow each independently changed behavior to a plausible failure. Credit existing assertions outside the diff. For a blocking gap, identify a supported caller or input, the consequence, why today’s tests would still pass, and the smallest assertion that would distinguish the outcomes. |
| **5. Review product direction** | Read relevant existing specs and agreed issue or PR decisions first. Distinguish current promises from proposed spec edits and future goals. Then read the two explanations and the material findings from 3 and 4. Consult a specific code path or test only when needed to verify a product judgment. | Answer in product terms. Whose workflow changes? Does an existing promise break? Is this a coherent slice of the intended design? Which decision needs a product owner? A verified broken promise can support a blocker. A deferred roadmap item normally warrants a question or an acknowledged scope choice. |

Passes **1, 2, and 4 can run concurrently** in separate contexts on the same base and head. Pass 3 waits for both recorded readings and the opening comment. Pass 5 waits for 3 and 4. The final poster groups findings about the same behavior and retains distinct code fixes and test remedies.

Build each blind reader’s inputs before invoking it. Filter both file contents and diffs, including unchanged files it can inspect. Repository Markdown instructions, historical commit messages, issue-derived briefs, earlier verdicts, and the shared GitHub comment can all reveal intent. Keep the original readings verbatim for that revision. A Markdown-only change gets an explicit statement that the first pass has no implementation evidence. Later passes can still assess a Markdown file that the product consumes, such as an agent prompt or displayed spec status. A PR without a linked ticket can proceed using the PR and available discussion.

A focused check on merged PR #4951 used two fresh Codex processes. Given only the trace route implementation and its filtered diff, the first described the schema move and preserved route behavior. Given only the route tests and an empty test diff, the second described the assertions and mock boundaries and said it could not infer what the revision changed. Neither input contained Markdown. This checked the two opening readings on one case. [PR #4951](https://github.com/re-cinq/lore/pull/4951)

## One editable GitHub comment per PR

- **Open once.** Pass 1 creates the review summary on the first review. Use the same comment ID on later phases, manual reruns and pushes. Fold the opening announcement and final summary into that comment. The existing GitHub review and check carry the formal verdict. [Current review contract](../specs/auto-review-loop/spec.md) · [GitHub comment update adapter](../libs/shared/src/outbound/project/lib/platform-github-issues.ts)
- **Keep the independent evidence visible.** For each head, show the two-sentence code reading first, then the test reading, intent comparison, concrete risks, product questions and final verdict as they arrive. Store pass outputs against the reviewed commit. Render updates from the stored results so concurrent completions preserve one another’s sections.
- **Recheck the current commit.** On a new push, update the same comment to show the new head and review status. A delayed result for an older head cannot change the new summary, resolve its threads, or approve it. A retried update or an ambiguous response after creating the comment must recover the existing Lore-owned comment. An incomplete run shows which pass is missing and cannot authorize auto-merge.

## Delivery and proof

| Slice | Observable acceptance case |
| --- | --- |
| **1. Independent readings and shared comment** | With identical code and tests, change only the issue, PR narrative or Markdown. Passes 1 and 2 still describe the same evidence. Adding a failing-case assertion changes the test reading while the code reading holds. A test-only or Markdown-only PR produces an honest scope statement. A retry and a second push retain one comment ID. |
| **2. Intent comparison** | A maintainer explicitly defers a requirement in an issue comment. Pass 3 recognizes the decision. Without that decision, it asks about the conflict. Its comparison leaves the original readings intact. |
| **3. Independent negative-test review** | Replay the same correct implementation with and without one meaningful refusal test. The reviewer identifies the missing assertion only on the variant that lacks it. A mixed PR also gets evidence for each changed behavior before findings are prioritized. |
| **4. Product review and verdict** | A PR that breaks a shipped user promise and one that delivers an agreed first slice of a future feature receive different judgments. The product reviewer cites the promise and observed consequence. The final check requires complete evidence for the same head. Cover retries, stale results and the existing budget-exhaustion approval path when exercising an incomplete review. [Run settlement](../apps/stations/src/code-review/run-settled/station.ts) |
| **5. Shadow pilot and rollout decision** | Exercise automatic reviews, manual reviews and rechecks through the effective pack. During shadow evaluation, record the proposed verdict alongside the current line’s decision. Verify one comment across phases and pushes, preserved human replies and rejection of stale writes. [Review starter](../libs/shared/src/work/review/floor-review-start.ts) · [Final posting station](../apps/stations/src/code-review/post-review/station.ts) · [Internal pack configuration](../deploy/clusters/internal-cluster.values.yaml) |

For the pilot, freeze prompts before a maintainer selects fresh cases. Include a sanitized delegated-auth change with an unchanged consumer, a missing refusal test without a dangling citation, a mixed PR, an agreed scope reduction, and a clean refactor. Replay each three times against the single-pass baseline. Score whether each reviewer found the designated behavior and justified its severity. Record false blockers, duplicate findings, time and cost. The proposed release threshold is detection of every designated critical regression and material test gap in each repeat, with zero blockers on the clean controls. Keep enforcement in shadow mode if it misses that threshold.
