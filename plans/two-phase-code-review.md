# Two-phase pull request review

**Proposed for the code-review and code-review-recheck assembly lines**

A PR author gets two things from Lore. Early in the review they see, in two sentences, what a reader thinks their code actually does. At the end they see one verdict answering two questions. Does the solution deliver the intended behavior across the paths it affects? Which tests would catch it doing the wrong thing?

The first historical replay caught an undisclosed status change and a missing refusal test, missed a confirmed parser defect, and produced unsupported blockers. The pilot recommendation is shadow mode while the opening comment and blocking criteria are calibrated. [Replay results and sample GitHub comments](../docs/building-lore/two-phase-review-replay-2026-11-19.md)

Today one agent reads the diff, ticket, conventions and CI, then hands a verdict to the poster. An implementation-loop station already looks for missing refusal tests on loop-authored work. Its questions are reusable. The PR reviewer has a different job and a read-only checkout, including on PRs written by people. [Current review contract](../specs/auto-review-loop/spec.md) · [Review line](../libs/assembly-lines/src/floor-pipelines/code-review.yaml) · [Implementation-loop benchmark](../docs/building-lore/test-review-bench-2026-11-19.md)

## Phase 1. Read the solution, then compare it with intent

1. **Form an independent reading.** Give the reviewer the base and head commits and the source tree. Withhold the PR narrative, ticket, discussion, and earlier verdict until it has recorded its reading. Start at the changed behavior and follow callers, registrations, configuration, and side effects into unchanged files as needed. Ask what guarantee moved, who relied on it before, and whether another path still has that guarantee. A rename or a move can change what runs even when the edited function looks identical.
2. **Post exactly two sentences as a GitHub PR comment.** The first describes an observable outcome. The second describes the condition, exception, or downstream effect that matters most. Use plain language and name uncertainty when the code leaves it open. For example, “When a delivery is retried, the transcript keeps one copy of the turn. Each delivery still adds its usage to the billing total.” The posting service records the comment on the reviewed head before comparison begins. Keep findings and the verdict for the final review.
3. **Compare that reading with the ticket, PR title and body, and discussion.** After posting, read conversation comments and review threads, including replies and decisions that supersede earlier comments. Exclude Lore’s own summary from the evidence of intent. In the final review, say where the observed behavior agrees with the stated goal and cite the source and code path for any material discrepancy. If the sources disagree, surface the specific decision for the author. If there is no linked ticket or discussion, proceed with the available sources. Retry a failed retrieval and identify any material evidence still missing. A later recheck picks up author corrections.
4. **Look for a counterexample to the solution.** Pick the strongest assumption this particular change introduces and try to disprove it from the checkout. For a shared guard, follow a consumer that acts locally. For a retry, follow every durable effect of a second delivery. A reviewer can raise a risk outside any named category. Record the affected path, trigger, and consequence, or the evidence that discharged the concern. Keep unsupported speculation out of blocking findings.

## Phase 2. Independently challenge the tests

A fresh reviewer starts with the question “What could this code do wrong while every existing test still passes?” It derives cases from the change and its consumers before seeing phase one's findings, then reconciles the two lists. Read existing tests outside the diff as well as added, weakened, skipped, or deleted tests. For each material guarantee, identify the test and assertion that would fail. If there is a gap, name the entry point, setup, expected result, and any forbidden side effect. Check whether mocks bypass the very decision being tested. CI supplies execution evidence for the reviewed revision.

| Evidence on the PR | What the author sees |
| --- | --- |
| A reachable path violates an intended guarantee | A blocking code finding, with its trigger and consequence, even if CI is green. |
| The code appears correct, but a consequential wrong outcome would pass the suite | A blocking test gap describing the smallest regression test that distinguishes the outcomes. |
| An unchanged test reaches the affected decision and asserts the right result | Credit that evidence. The author can keep the existing test. |
| A material question depends on unavailable evidence | Identify the missing evidence and who can settle it. An incomplete review cannot approve. |

For delegated access decisions, consider an invalid session, a valid identity without access to the resource, and an allowed identity. The meaningful assertion covers both the caller-visible result and whether privileged work took place. For a retried delivery, inspect both the visible record count and the billed amount. These examples calibrate the method. Reviewers choose counterexamples from the change under review.

## Delivery in four pull requests

| Slice | Production change | Acceptance test |
| --- | --- | --- |
| 1. Publish the independent reading | Split the initial review into a code-only read, an idempotent comment post, and the solution review with ticket, PR, and thread context. Pass the recorded reading between visits. Keep the existing final poster. | Give the same code opposite PR descriptions. Both first comments describe the same behavior in two sentences. Only the misleading description produces an intent mismatch. The run log shows the post precedes comparison. Redelivering the post leaves one comment for that PR and head. |
| 2. Gate the first verdict on both reviews | Add the independent coverage station. Run it even when phase one finds a blocker. Have the posting service combine both reports for the same revision, group related findings, and retain their separate code and test remedies. | A code defect survives a clean coverage report. A missing negative test survives a clean solution report. Both appear together when present. Two clean reports produce one approval. A missing, malformed, or wrong-revision report, or an exhausted retry, produces no approval. |
| 3. Apply the same standard after a push | Extend the recheck line and approval-carry rules. Revisit changed guarantees, their consumers and tests, and unresolved findings from either phase. Publish a fresh reading for a materially changed head. | A follow-up changing only tests can introduce or close a blocker. Fixing only one of two blockers keeps the PR at changes requested. A later push supersedes old evidence. A pure rebase can carry approval only when the reviewed change and relevant guarantees still match and the previous review completed both phases. |
| 4. Prove the improvement in the active pack | Run the current and proposed lines on identical PR snapshots. Exercise a pilot repository with the effective pack, including manual review, automatic review, and recheck. Ship the defaults and matching pack definitions through their existing release paths. | Inspect the actual two-sentence comment, final GitHub review, and `lore/code-review` check. A transient post failure creates no duplicate. A partial run cannot authorize Lore auto-merge. Verify effective station and prompt versions before widening rollout. |

Each slice changes observable behavior. Start with its failing acceptance case, then exercise the line and station contracts. Use deterministic fixture outputs to test routing, revision checks and publication. Use actual reviewer runs to judge whether the prompts find a defect. Keep test execution in CI and review checkout access read-only. Alongside the line YAML and [agent defaults](../libs/shared/src/agent-defaults), the implementation touches the [review starter](../libs/shared/src/work/review/floor-review-start.ts), [post-review station](../apps/stations/src/code-review/post-review/station.ts), and [internal pack configuration](../deploy/clusters/internal-cluster.values.yaml). The delivery contract already has a tracking story. [Issue #4519](https://github.com/re-cinq/lore/issues/4519)

## How to tell whether this catches surprises

- **Calibration.** Use a sanitized historical delegation change whose affected consumer is outside the diff, a correct fix with only the negative test removed, and a repaired version with a meaningful existing test. Score the code finding and the coverage gap separately. Two public tickets supply independent examples of missing refusal coverage and a retry affecting multiple writes. [Issue #4948](https://github.com/re-cinq/lore/issues/4948) · [Issue #1394](https://github.com/re-cinq/lore/issues/1394)
- **Blind evaluation.** Have a maintainer select additional cases from different failure families after the prompts are frozen. Withhold issue text that reveals the answer and include clean controls, including a change with no behavioral effect. Run each case three times. Score findings against the affected behavior and evidence, independently of wording. Record misses, false blockers, duplicate findings, time, and cost beside the current line.
- **Proposed release threshold.** In all three runs, catch each designated critical regression and material test gap, including the held-out cases, and issue zero blockers on the clean controls. Report the sample size and observed time and cost to the pilot owner. A missed critical case or a false blocker keeps the pilot from widening.
- **After rollout.** Sample approved PRs as well as disputed blockers. For each confirmed escape, record the assumption that went unchallenged, the evidence the reviewer could have seen at the time, and which phase missed it. Reserve a fresh holdout for the next evaluation. When a recurring invariant can be checked mechanically, give it a focused CI test or lint rule and let the reviewers spend their attention on the next unfamiliar change.
