Who owns what, and what each layer refuses to do

The relations hold because each layer has a short list of things it will never do. That is what lets any of them be swapped or run elsewhere.

One run, across the layers

An event comes in, the floor decides the next node and puts a dispatch on its queue, a worker claims it, and the report advances the walk. The same ten steps for every node of every line.

#What happensWhere
1Something posts an event: a PR opened, a plan approved, a schedule tickLore → Floor
2The loop routes it: start a run, or join the run already open on this subjectFloor
3The walk replays the run's visits and picks the next nodeFloor
4A visit opens; its brief is frozen, station and agent definition pinned by content hashFloor
5A dispatch goes on the queue, tagged. Nothing is pushedFloor
6A worker claims it by offering tags: the cluster-agent for an agent node, a Lore station for a service nodecluster-agent · Lore
7For an agent node: one Agent resource → Job → Pod. The subsystem runs itai-agent-subsystem
8The pod reads its brief, posts turns, cost and files to the sink, and reaches Lore through lore-mcp for context and memorypod → Floor · Lore
9Its lifecycle event ends the visit; the report is written and the walk advances in one transactionFloor
10The next node's dispatch, or the run settles and Lore hears it through a line of its ownFloor → Lore

Three kinds of node

agent

An agent station

The cluster-agent claims it and creates one Agent resource. The pod does the work and reports back itself.

service

A service station

One of Lore's workers claims it and runs one function: post a review, open a PR, file issues, merge. Every GitHub action a line takes is one of these.

human

A human node

Dispatches nothing and waits with no deadline. Lore serves the page: the plan editor, the PR. A person answers with a report or an event.

Visits are the truth. A run's status, bag, current node and cost are never stored; they are replayed from its visits. Every visit pins its station and agent definition by content hash, so a run can always be explained.

Code review: three short lines on one pull request

The simplest family, and the one every other line relies on. One agent station reads, one Lore station posts. Everything GitHub-shaped is a service station, so the agent never touches GitHub.

teal = agent station · grey = Lore service station · amber = retry edge
trigger

A PR opens or leaves draft

GitHub's webhook lands on Lore; the stations service starts the line with the PR as subject. A second start for the same PR joins the open run instead of racing it.

review

Reads the whole change in a clone

Changed files, callers, tests, the spec statements they touch, the CI verdict through lore-mcp. Cannot install, build or run the suite. Ends with APPROVED or CHANGES_REQUESTED and its findings.

post-review

Posts the verdict, inline

Each finding on its line with a suggestion; the review names the model and the run. When the run settles, a fourth line closes the check run and the announcement comment.

humanReply in any thread, comment @lore review to re-run, or request changes to stop the factory on that PR. Merge stays a person's call unless lights-out is on.

Planning: a plan written together, then a spec, then tickets

The agent analyses the repository and the knowledge graph and drafts; people and the agent edit the same versioned plan live. Two human nodes hold the line until a person acts: the plan's approval and the spec's merge.

analyze

Each pass reads, then proposes

The repo, similar specs and past outcomes from the knowledge graph; it proposes sections or asks the questions it cannot answer. Every button on the plan page is an event into the one open run.

author

People and the agent edit the same plan

Every change is a version. A refine request sends the agent round again; Validate asks for a feasibility check whose result lands as comments. Approval is the decision.

write

The approved plan becomes a spec

In the fixed format, opened as a pull request people review like code. Sent back, it returns to the plan.

decompose

The merged spec becomes tickets

Each with "done when these pass", sized for one implementation run. The issues station files them; the backlog loop picks them up.

Implementation: one ticket, one line, CI judging every push

The backlog loop starts one run per ticket. Each visit is a fresh agent in its own pod doing one bounded job; the pull request's own build decides the next node. The line never merges.

dod

Define done as failing tests

Reads the ticket and the spec; writes the fewest red acceptance tests that mean "done" and a one-page brief every later agent reads. A ticket it cannot turn into tests is blocked with the reason.

tdd-round

One red-green-refactor round

Never edits an acceptance test to make it pass; never runs lint, typecheck or the suite, because CI does on every push.

await-ci · await-pr

Parks, costs nothing

No pod while CI builds or review runs. Green moves on; red goes to the next round, a repair, or a fix from CI's report. Code review runs on this PR like any other.

retrospective

Writes back what happened

Episode, memory and cost into the knowledge graph. Then auto-merge is evaluated, or a person merges.

humanPush to the branch, request changes to stop the line on that PR, or take over a ticket labeled lore:blocked; remove the label to hand it back.
