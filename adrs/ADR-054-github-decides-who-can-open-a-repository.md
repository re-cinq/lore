# ADR-054: GitHub decides who can open a repository, and every caller that is not a person has its own narrow token

This is a draft for review. The points marked "Decided" are settled; the rest is proposed. It sets out how Lore answers "may this caller do this to this repository", for people and for the callers that are not people, and in what order to build it. It amends ADR-053.

## Background

Lore acts on GitHub with its GitHub App, which can read and write every repository it is installed on. Who may ask Lore to use that access is decided by Lore alone, and today the answer is too wide in three ways.

- **A person's access is a list taken once.** At sign-in lore-api reads the repositories the person can open through a separate OAuth App with the `repo` scope, stores the names on the session and discards the token (ADR-053). The list is never refreshed, stops at 1000 repositories, and is checked on the run routes only. Every other route trusts the session's scope.
- **Every session has the `admin` scope.** Lore has no roles, so a member of the organisation can use every route.
- **Most callers that are not people share one token.** The value of `lore-ingest-token` is every scope with no expiry and no owner, and lore-api accepts it from its environment without a database row. The MCP gateway, the stations service, its scheduled jobs, every onboarded repository's CI, every developer's laptop and the VS Code extension hold it. The floor, the agent subsystem and the gateway's own front door already have tokens of their own.

A first change, already written, puts one question ("can this person open this repository") behind every route that names a repository in its path, and answers it for a repository outside the sign-in list by asking GitHub, as the App, what the person may do there. It closes the widest gap, but Lore still makes the decision, still does not tell read from write, and still learns of a removed grant only when it asks again.

## Proposal

### 1. A person signs in through the GitHub App, and lore-api keeps their user access token

A GitHub App can issue a user access token: a token that acts as the person, limited to what both the person and the App may do, and only in accounts where the App is installed. GitHub checks every call made with it against the person's permission at that moment.

- lore-api runs the App's own web authorization flow in place of the OAuth App's, with the App's client id and client secret, which are settings of their own and are neither the App id nor the OAuth App's pair. The separate OAuth App and its `repo` scope, which reaches every repository the person has anywhere, are retired. An installer creates one GitHub App and nothing else.
- The token expires after 8 hours and comes with a refresh token that lasts 6 months and is replaced on each use, but only when the App has expiring user tokens switched on. That setting becomes a requirement of the install. lore-api refuses a sign-in whose token answer carries no expiry or no refresh token, so a misconfigured App cannot leave a token that never expires.
- lore-api stores both tokens encrypted (AES-256-GCM, key in a Secret of its own) in a table beside the session row. The session row records the person's GitHub numeric id, and everything done to "every session of a person" finds them by that id, never by login.
- Refresh, sign-out and revocation all take the same row lock, and a session marked ended can never be refreshed back to life. A refresh whose outcome is unknown (the request was sent and no answer came back, or lore-api stopped before the new pair was stored) ends the session and the person signs in again, because GitHub may already have cancelled the old pair. Sign-in, minting a token, the cleanup after a removal and a revocation all take one lock per person, so a person being removed cannot gain a new session or token at the same moment.
- lore-api refreshes a person's token before it uses it, when the access token expires within five minutes. Proposed 2026-11-19: when GitHub refuses the refresh token as invalid, expired or revoked, the session ends and the person signs in again; when the refresh request never left (GitHub could not be reached) or GitHub answers with a server error, the request is refused as "cannot check right now", the session and its tokens are kept, and the next request tries again; when the request was sent and no answer came back, the outcome is unknown and the session ends.
- Tokens are deleted at sign-out, when GitHub sends `github_app_authorization` (the person revoked the App), and by a scheduled sweep once the session has expired. Today an expired session row is only ignored, never deleted.
- `github_app_authorization` is sent to the App's own webhook address, which installs do not set today because Lore's events arrive through a webhook on each repository. Step 3 adds the address and a signing secret of its own, kept apart from the repositories' webhook secrets. lore-api verifies the signature before it reads the event and accepts two secrets while one is being replaced.
- This reverses one line of ADR-053, "the GitHub token never outlives the callback request". The reason for that line was to hold as little as possible. The cost of holding nothing is that Lore must guess at access; the proposal is to hold a token GitHub has already narrowed, protect it, and let GitHub answer.

### 2. GitHub answers the access question

- **Which repositories a person sees and reads.** `GET /user/installations/{installation_id}/repositories` with the person's token lists the repositories of this installation the person can access, with their permission on each. Lore's lists (onboarded repositories, repositories available to onboard, search and inbox results) are filtered to that list, and so is every read of what Lore has stored about a repository, because those reads never reach GitHub and nothing else would refuse them. The list is kept per session for at most five minutes. Past five minutes without a fresh answer from GitHub, reads are refused, not served from the old list. So a removed grant can still read Lore's stored data about that repository for up to five minutes, and no longer. Five minutes is accepted (decided 2026-11-19).
- **What a person may do.** Each route states the level it needs, and the rule is that Lore never does for a person what GitHub would refuse them: `read` to see, `write` for what a person with push access can do (commit, branch, pull request, issue, starting a run), `admin` for what only a repository administrator can do. Onboarding sets repository secrets and variables and creates a webhook, so onboarding and re-onboarding need `admin`, as do the repository's settings in Lore and auto-merge. The rule covers every route that names a repository: one that changes nothing needs `read`, one that changes anything needs `write`, and `admin` is a named list (onboarding, the repository's settings, creating its webhook, and the routes that today need Lore's `admin` scope), held by a test that fails when a repository route has no level. The level applies however the repository is named, in the path, the payload or the query or through a record the request names, and an answer that spans repositories holds only rows of repositories the person can read. The guard that already sits in front of every repository route compares the level GitHub reports with the level the route needs. A `write` or `admin` action asks GitHub at the time of the action, not from the cache.
- **Things that belong to no repository** (agent definitions, tokens, organisation settings, pools, the audit log, pack sync) stay open to every signed-in member for now, as they are today. Decided 2026-11-19. It is a known gap, not a goal: any member can still mint a token with any scope, so step 4's narrow credentials do not bind a member who wants a wide one. What a member mints is tied to them, as the next two points say. Narrowing it later to owners of the GitHub organisation is a change of one check.
- **Membership of the organisation is checked throughout a session, not only at sign-in.** Today it is asked once, and a session lasts up to 30 days, so a person removed from the organisation keeps Lore until the session ends. With the person's token, lore-api asks again whenever it refreshes their repository list, so no request is served on a membership answer older than five minutes. The next request of a person GitHub no longer reports as an active member is refused, and it ends every session they have and revokes the tokens they minted. Nothing rechecks on a schedule: a session nobody uses is ended at its next request or by its own expiry, never honoured. Past five minutes without an answer from GitHub, the request is refused and nothing is ended. An open live connection follows the same five-minute rule before each frame, and is closed when its session ends: a connection records the session that opened it, and the end of a session is announced to every lore-api replica. Asking with an App's user token needs the App's organisation permission Members (read), which installs leave off today, and an owner of the organisation has to approve it. An answer of "not permitted" is reported as a fault of the install, not treated as "not a member".
- **A token a person mints belongs to that person.** Today a minted token records its maker as the constant "admin", has no expiry unless one is asked for, and outlives the person's membership, so anyone can keep Lore after leaving by minting a token first. From step 3 a minted token records its maker's GitHub numeric id. When the token is used and the last answer is older than five minutes, lore-api first asks GitHub, as the App, whether that person is still an active member, and when they are not it refuses the request and revokes every token they minted along with their sessions. A token nobody uses is not looked at, so it is revoked at its first use after the person left, never honoured. Tokens the install itself provisions (the stations token, an operator's emergency token) are a separate kind and are not minted through this route. A token minted before step 3 has no known maker, so it cannot be tied to anyone: the step-3 upgrade revokes every such token in the database, as it ends every session, and people mint again (decided 2026-11-19). This is separate from the token lore-api reads from its environment, which step 4 withdraws.
- **A repository is identified by GitHub's numeric id**, not its name, wherever access is recorded or a credential is bound, so a renamed, transferred or re-created repository does not inherit another's access. Lore's repository rows are keyed by name today. The migration adds the id, fills it by asking GitHub through the installation, and a row whose id cannot be found or belongs to another row is closed to everyone until an operator resolves it.
- **Lore's own scopes stay for callers that are not people.** A person's session keeps `admin` for the routes that belong to no repository, and on a repository route it is GitHub's answer that decides, not the scope.

### 3. Who performs the action: the person, with their own token

Decided 2026-11-19: when a person asks for a change, lore-api makes it with that person's token. GitHub then enforces everything itself, including branch rules as they apply to that person, and attributes the change to them. Lore needs no rule of its own for these: a person who is not an administrator of the repository cannot onboard it, because GitHub refuses the secret, the variable and the webhook.

This covers every change lore-api makes on GitHub while it handles a person's request: onboarding, creating or repairing a repository's webhook, a branch, a commit, opening a pull request, filing or changing an issue. The same route called by a caller that is not a person makes its change as the App.

It does not cover agent runs, and the reason is the size of the token. An App installation token can be narrowed to one repository and a few permissions; a person's token cannot, and reaches every repository of the installation that the person can access. An agent reads repository content that may be written to steer it, so it must not hold that. Agent runs keep the App's token for one repository (decided 2026-11-19), under these rules:

- A run records the GitHub numeric id of the person who asked, never only their login, and the repository's id. The floor asks lore-api for the run's GitHub credential at each station, and lore-api asks GitHub, as the App, what that person's permission on the repository is before it mints one. It mints none for a run that is no longer active, and a token whose minting overlaps the run's end is revoked, not handed over. The check does not need the person's token, so a run goes on after its starter signs out and stops when their access does: when GitHub reports less than `write`, no credential is minted and the run is cancelled.
- When a run is cancelled or ends, lore-api revokes the installation tokens it minted for it, so a copy of the token is useless.
- Between two checks an agent can still write for up to an hour with the token it holds, and GitHub applies branch rules to the App, not to the person. This is the remaining gap of letting agents write directly.

Not in this decision: closing that gap means agents hold no GitHub token and every push and pull request goes through lore-api, which checks the person each time. That is a larger change to how agents work. It stays a later option and is not part of this work.

Whether a user token of the App can set a repository secret and create a webhook has to be confirmed on a real installation.

### 4. Callers that are not people

A token that is not a person's has no GitHub identity to honour. Each such caller gets a credential that can do its one job and nothing else, and none of them is the shared admin token.

| Caller | Today | Proposed |
| --- | --- | --- |
| A repository's CI (ingest, test report, trace impact) | the admin token as a repository secret | GitHub Actions' own OIDC token: the workflow asks GitHub for a signed token that names its repository, and lore-api verifies it and allows ingest for that repository only. No secret is stored in the repository. Where OIDC is not available, a stored token of a kind of its own, bound to that one repository and accepted only on the routes an identity token is. The callers are the two jobs of the ingest workflow, the test report, trace impact and the spec-link check. |
| Agent pod to the MCP gateway | one bearer for all agents; the gateway then uses the admin token | The run's own short-lived token, which the floor already issues per visit. The gateway checks it, learns the run and its repository, and calls lore-api with a token bound to that repository. An agent can read and write Lore's context for its own repository only. |
| Agent pod to GitHub | an installation token for one repository, 1 hour, with write access to contents, issues, pull requests and workflows | The same token, minted only after GitHub confirms the person who started the run still has `write`, and revoked when the run ends (section 3). A run Lore starts itself follows the rules below the table. |
| Stations service and its scheduled jobs (the courier CronJobs) | the admin token | A named system token with the scopes its sweeps use, accepted only on the routes its jobs call, a list a test holds, and read only by the stations service and its scheduled jobs. It works across repositories by design, never leaves the cluster, and can be rotated on its own. |
| The floor to lore-api | two shared tokens | unchanged in kind: system to system, inside the cluster. |
| The web UI's server | the person's session, plus the App's private key for its own GitHub reads | the person's session only. The UI asks lore-api, which reads GitHub with the person's token. The UI holds no GitHub credential. |
| A developer's laptop (the local MCP server and the VS Code extension) | the admin token, copied from the cluster into git config or the editor's settings | The person signs in from the terminal or the editor by a pairing of Lore's own (proposed 2026-11-19): the client shows a short code, the person confirms it in the web UI where they are signed in, and the laptop holds a session for that person. It uses nothing of GitHub's device flow, so it works the same on GitHub Enterprise Server. The session is kept in the editor's or the operating system's credential store. It can do what they can do. The clients and the install script stop reading and writing the copied token, and remove it after the first sign-in. |
| GitHub's webhooks to Lore | one signing secret for all repositories, readable through the API | a secret per repository, stored encrypted against the repository's id and never served by the API. |
| The static admin token | every caller above, and the web UI's settings page, which shows it to any signed-in member | removed. The settings page and the settings route stop showing and accepting it. lore-api stops accepting a token from its environment. An operator who needs emergency access mints a token with a command inside the cluster: it names the operator, expires within hours (4 by default, 24 at most; proposed) and is written to the audit log. |

**Runs Lore starts itself.** Today a pull request opened by anyone, a fork included, starts a review when auto-review is on for the repository, with no check of who opened it. The review agent's token is read-only, and the write token goes only to the follow-up run that a trusted reviewer starts. What an outsider gets today is agent time at the installer's cost, and a say in a verdict that Lore then posts under its own name as an approving review and a passing check. The rules proposed:

- **Whether a run starts.** Each repository says whether a pull request from someone without `write` starts a review at all; the default is no.
- **What the run may do.** A run started by an event is trusted only as far as the person behind the event. Without `write`, the agent gets a read-only token and no tool that writes, in GitHub or in Lore, and Lore posts its findings as a comment, never as an approval or a passing check.
- A scheduled job runs as the stations token with a fixed list of operations. A run a schedule starts has no person behind it, so it gets the GitHub access its station asks for, for its one repository.

**The Actions identity token.** lore-api accepts it only when all of these hold:

- the issuer is exactly the configured GitHub host's, and the signature matches the keys that issuer publishes, fetched and refreshed from it, at most once a minute for a key it does not know, and kept for an hour at most (proposed);
- the audience is this Lore install's own address, so a token minted for another service is refused;
- it is within its validity period (`iat`, `nbf`, `exp`), which GitHub sets in minutes;
- `repository_id` and `repository_owner_id` match an onboarded repository. A GitHub Enterprise Server version without those claims does not use the identity token at all and uses the per-repository token;
- what it allows depends on where the run is. From the repository's default branch it allows the ingest routes, which change what Lore knows about the repository. From any branch or pull request of the repository it allows only the routes Lore's checks call and that change nothing (trace impact, spec-link parsing). Which workflow file runs does not matter: whoever can change a workflow on the default branch can already write to the repository;
- the event is not a pull request from a fork. GitHub gives such a run no identity token and no secrets, so trace impact does not run for a fork's pull request, as today.

The workflow's first job posts to `POST /api/ingest`, which names its repository in the payload; the token is accepted there only when the payload names the token's repository. It buys the ingest routes of that one repository for the token's own short life, and lore-api issues nothing longer-lived in exchange. Within that time the token can be sent again: an ingest run makes many requests, and sending it again gives a holder nothing beyond ingest for that repository, which is what the workflow itself does. The ingest client asks GitHub for the token itself and asks again when it is about to expire.

**The run's gateway credential.** The floor already signs a token for each visit of a run. The proposal is that the gateway verifies that signature itself (the floor's signing key becomes a key pair, and the gateway holds only the public half), reads the run id, the repository id, the scopes and the expiry from it, and forwards it to lore-api, which verifies it the same way and applies the repository guard to it. The token lasts as long as the visit and is refused after the visit ends. The format, the key rotation and what a long visit does at expiry are to be written as a spec of their own before step 4 starts.

### 5. Order of work

1. **The guard and the single question** (written, in review): every repository route asks, and onboarding asks.
2. **Levels**: routes state `read`, `write` or `admin`; the answer still comes from the App asking about the person, and from step 3 it comes from the person's own token. Removes the route that serves the webhook secret.
3. **User access tokens**: sign-in through the App, token storage and refresh, lists and reads filtered by GitHub's list. Sign-in still admits only active members of the organisation, and a member keeps the routes that belong to no repository. The web UI stops holding the App's key. There is no period in which both sign-ins decide access: the upgrade ends every existing session, because an old session has the `admin` scope and no GitHub token to check with, and everyone signs in again. It also revokes every token minted before it, which has no known maker, and whoever relies on one mints a new one. The OAuth App's settings stay in the values file for one release so a rollback can sign people in, and a rollback is a step of its own that runs before the older release serves a request: it ends every session, revokes every token a person minted since the upgrade (the older release cannot check its maker's membership and would honour it for ever), and deletes the stored GitHub tokens. Minted tokens carry a mark of the release kind that made them so that this set can be found. The release being replaced cannot be told to stop writing sessions, so the upgrade's cleanup and the rollback step both run with lore-api stopped, at the cost of a short outage at that one upgrade.
4. **Callers that are not people**: CI by OIDC, the run-bound gateway credential, the stations token, sign-in by pairing for laptops and the editor, the rule for runs Lore starts itself, and a webhook secret per repository. It takes two releases so that a rollback works. The first only adds: lore-api accepts both the shared and a per-repository webhook secret, and both the stored token and the identity token from CI. Repositories and their workflows are moved once that release is the one a rollback returns to. Each repository's webhook is moved to its own secret while lore-api accepts either the old or the new one, and the shared secret is dropped when no webhook uses it. From the first of the two releases, a newly onboarded repository gets the new workflow and its own webhook secret directly, and never the shared token. Existing repositories are moved by a job that, for each repository, sets its webhook to its own secret, opens the pull request that changes its installed workflow, and deletes its stored copy of the shared token once the new workflow has ingested, no workflow file on its default branch still reads it and the repository has not used it for 30 days; the job records its progress per repository, tries a failed step again, and lore-api shows an operator each repository's state and what still holds it back. A webhook's new secret is stored before GitHub is changed and the repository counts as moved only once a delivery signed with it has been verified. The shared admin token is withdrawn last: lore-api records every use of it by caller, and it is removed after 30 days in which none is recorded (proposed) and every repository is moved.

Steps 1 and 2 need no change to an install. Step 3 needs, on the App: a callback URL, its client id and a client secret, expiring user tokens switched on, a webhook address and its signing secret, and the organisation permission Members (read) approved by an owner; and a database migration. Before anything is stopped, the upgrade checks through GitHub's API, as the App, that the permission is granted, and that the client id and secret are set, and does not start otherwise. lore-api cannot read most of these settings back from GitHub, so they are checked three ways: what is in the values file, at start, where lore-api refuses to run in the new mode when one is missing; the App's permissions and webhook, through GitHub's API, as a warning in the log and on the settings page; and the rest where they show, with a sign-in refused when its token has no expiry. The install guide gets a checklist an operator runs before the upgrade. Step 4 changes the workflows Lore installs in repositories.

Each step is done when tests show its boundary holds, not when the code is merged:

- **Levels**: for every route, a person one level below what it needs is refused; a person without repository admin cannot onboard.
- **User tokens**: a removed grant refuses the next write and, after five minutes at most, every read; reads are refused when GitHub has not answered for five minutes; two refreshes at once leave one valid pair; a sign-out during a refresh leaves no token; an expired session's tokens are gone after the sweep; a session whose access token expired goes on while its refresh token is valid, ends when GitHub refuses the refresh token or a sent refresh got no answer, and is kept when the request never left or GitHub answered with a server error; a member who is no repository's administrator still opens the organisation-wide pages and a non-member cannot sign in; no request of a person removed from the organisation is served on a membership answer older than five minutes, their next request is refused and ends every session they have, a session left unused is refused at its first use, and a token they minted is refused and revoked at its next use, including one left unused since before they were removed; a token minted before the upgrade is refused after it; a minted token names its maker's GitHub id; a membership question GitHub refuses for want of permission is reported as an install fault and admits nobody; an old session is refused after the upgrade; after a rollback no session, no token minted since the upgrade and no stored GitHub token remains; a revocation event with a bad signature is ignored.
- **Callers that are not people**: a workflow's token for one repository is refused for another, and so is an agent's; an identity token with the wrong issuer or audience, or expired, is refused, and one from a branch other than the default is refused on the ingest routes; an ingest run that makes many requests with one identity token, and outlasts it, completes; a run whose starter lost `write` gets no further credential and its minted tokens are revoked; a pull request from someone without `write` starts nothing by default and never yields an approval; a webhook signed with the old secret is accepted during the move and refused after it; after a rollback to the first step-4 release, moved repositories' webhooks and workflows still work; an emergency token names its operator in the audit log; nothing in a rendered install holds the admin token.
- **What operators can see**: counts of refused requests by reason, failed token refreshes, refused identity tokens, failed revocation events, uses of the shared admin token by caller, and repositories still on the shared webhook secret.

## Rationale

- **GitHub is already the record of who may touch a repository.** A second record in Lore can only be the same or wrong.
- **A removed grant takes effect at once** for a change a person asks for, within five minutes for what they can read, and at the next station for an agent run they started.
- **The sign-in asks for less.** The OAuth App's `repo` scope covers a person's repositories everywhere. The App's token covers only where the App is installed.
- **One leak is one repository.** With the proposed credentials, a workflow's token, an agent's token or a repository secret opens one repository's data in Lore, where today each opens the whole install.

## Consequences

- lore-api holds encrypted GitHub tokens for signed-in people. Its database and the encryption key become more sensitive, and a backup of the table without the key must be useless.
- Every read depends on an answer from GitHub no older than five minutes. If GitHub cannot be reached for longer, Lore refuses reads and changes for people until it can.
- More calls to GitHub, counted against each person's own rate limit, not the App's.
- Changes a person asks for appear on GitHub under their name, not the Lore bot's. Changes made by agents and scheduled jobs stay under the bot's.
- An existing install has to change its GitHub App's settings and its values file once, and an owner of the organisation has to approve one new permission for the App. At the step-3 upgrade everyone signs in again and every token minted through Lore has to be minted again.

## Open Questions

- **When to narrow the organisation-wide pages**, which stay open to every member for now.
- **GitHub Enterprise Server**: user access tokens and their refresh are documented there. Those, and Actions OIDC, have to be confirmed on a real server of the versions our installers run.
- **Encryption key**: generated by the chart like the other tokens, or required from the installer?
