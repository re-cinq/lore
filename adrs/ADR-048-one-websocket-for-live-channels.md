# ADR-048: One WebSocket carries the browser's live channels

This ADR replaces the run page's Server-Sent Events stream with one WebSocket per browser tab, served by lore-api at `/api/ws`, that multiplexes named channels: a `run` channel forwards an assembly run's pod events and transcript to everyone registered for that run, and a `plan` channel tunnels the plan editor's collaboration protocol, so a navigation from a plan to its run keeps the connection.

## Context

ADR-037 chose SSE for run observability and rejected a WebSocket as a duplex channel nothing needed. Two things changed since. The plan editor ([ADR-047](ADR-047-plans-hosted-by-lore-api.md)) opened the stack's first WebSocket, straight from the browser to lore-api's public host, so the ingress, the token ceremony and the client library the rejection counted as costs are already paid. And the run page and the plan page are one flow — a plan's page links to its run — yet each opened and tore down its own connection on every navigation, and the run page reached lore-api through a Next.js proxy hop the plan page never needed.

On the server, each SSE subscriber held its own `LISTEN` subscription and re-read the database on every notification, so a run with five viewers cost five re-reads per pod event.

## Decision

### One socket, many channels

- lore-api serves one WebSocket upgrade at `/api/ws` on its own listener, beside the plans library's mount, and leaves any other upgrade path to the mount that owns it ([validated by leaves a foreign upgrade path to the mount that owns it @55d296be](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L297)).
- Every message is one JSON text frame with a client-chosen channel id. A client opens a channel with `open` (kind `run`, `runs` or `plan`), closes it with `close`, and sends a plan channel's bytes as base64 with `send`; the server answers `opened`, `frame`, `data`, `closed` with a reason, or `error` with a code. The contract is published in OpenAPI as `LiveClientMessage` and `LiveServerMessage` beside `RunStreamFrame`, with the socket named by a root `x-websocket` extension, so the web-ui reads generated types ([validated by reads a run open with its token and cursor @26f64762](../apps/lore-api/src/work/assembly-line-station/protocol.test.ts#L11), [validated by reads a plan open, a send and a close @8d7545a7](../apps/lore-api/src/work/assembly-line-station/protocol.test.ts#L26), [validated by encodes every server message type as JSON the schema accepts back @8ae19ba9](../apps/lore-api/src/work/assembly-line-station/protocol.test.ts#L130), [validated by round-trips bytes through base64 @25b423cd](../apps/lore-api/src/work/assembly-line-station/protocol.test.ts#L168)).
- A message that is not JSON, names an unknown type, opens a plan-run without a token, or carries a non-numeric cursor is refused as `bad_message`; a channel id already open is `channel_in_use`; a ninth channel on one socket is `too_many_channels`; an open past the socket's rate limit is `rate_limited`; a send or close for a channel the socket does not hold is `unknown_channel`. None of them takes the socket down ([validated by returns null for non-JSON, an unknown type, a non-numeric cursor, and a plan-run open without a token @f646b5d9](../apps/lore-api/src/work/assembly-line-station/protocol.test.ts#L117), [validated by answers a malformed message, an unknown channel, a reused id and a channel past the cap with errors @bba0ee5e](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L241), [validated by refuses an id already open and any id past the cap @10e28f39](../apps/lore-api/src/work/assembly-line-station/channel-registry.test.ts#L7)).
- The socket pings every 25 seconds and terminates a peer that misses a pong; a socket that goes closes every channel it held, once, and a channel a handler ended itself is forgotten without closing it again ([validated by terminates a socket that stops answering pings and closes its channels @bba0ee5e](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L315), [validated by closes every channel once and forgets them when the socket goes @16786f5d](../apps/lore-api/src/work/assembly-line-station/channel-registry.test.ts#L19), [validated by forgets a channel its handler ended without closing it again @19ba6dc3](../apps/lore-api/src/work/assembly-line-station/channel-registry.test.ts#L33)).

### The socket knows the person *(added 2026-11-14)*

- The socket is opened on the UI's own host, `lore.gcp.re-cinq.com/api/ws`, which the ingress routes to lore-api, so the httpOnly `lore_session` cookie rides the upgrade and the browser's script never holds the token. lore-api reads the cookie by hand, keeps the person's session token on the connection, and neither logs it nor sends it back ([validated by finds the session in a Cookie header that holds three cookies @2def5bab](../apps/lore-api/src/work/assembly-line-station/socket-session.test.ts#L5), [validated by answers undefined for a header with no lore_session @4ce9b8ac](../apps/lore-api/src/work/assembly-line-station/socket-session.test.ts#L11), [validated by answers undefined for a missing header @45e0bb7f](../apps/lore-api/src/work/assembly-line-station/socket-session.test.ts#L15)).
- An upgrade that carries the cookie from an origin the login route would not send a person back to, which is another site trying to use the person's cookie, is refused with `403`; a cookie from the UI's origin or a local UI over http is admitted, and an upgrade with no cookie is admitted from any origin exactly as before, its channels then needing minted tokens ([validated by refuses the upgrade of a cookie socket from https://evil.example with 403 @c8744c0f](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L463), [validated by admits a cookie socket from an allowed origin @edb60293](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L479), [validated by admits a socket with no cookie from any origin @876d89c8](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L475), [validated by allows the UI's origin and a local one, and refuses another site, the string null and no origin @5e0f90ac](../apps/lore-api/src/work/assembly-line-station/socket-session.test.ts#L23)).
- A `request` message (an id, a method, a path under `/api/` and an optional body) asks for any lore-api route, and one `response` with the same id answers it. lore-api runs the route in-process with the person's session token as its bearer, so the route's own scope check, validation, rate limit and repo checks apply unchanged, and a session revoked by sign-out answers `401` on the next request. The route's status and body come back untouched, a payload that is not JSON as a string ([validated by answers Ana's GET /api/floor-runs over the socket with the route's 200 and rows @6d16ceb3](../apps/lore-api/src/work/assembly-line-station/socket-request.test.ts#L60), [validated by answers the route's 403 untouched @f4771d94](../apps/lore-api/src/work/assembly-line-station/socket-request.test.ts#L97), [validated by sends the body of a POST to the route @60180aaa](../apps/lore-api/src/work/assembly-line-station/socket-request.test.ts#L104), [validated by answers a payload that is not JSON as a string @638f7d46](../apps/lore-api/src/work/assembly-line-station/socket-request.test.ts#L110), [validated by answers a request on Ana's cookie socket with the route's status and body @5bcf5902](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L492), [validated by reads a request and rejects one whose path is outside /api/ @4c6e7f5c](../apps/lore-api/src/work/assembly-line-station/protocol.test.ts#L100)).
- A request on a socket with no session is answered `401`, one for `/api/auth/`, `/api/webhook`, `/api/ws` or a path that leaves `/api/` once its dots are resolved `404`, and a route that throws `500`, with the socket and its channels kept open ([validated by answers 401 to a request on a socket with no session @13204a35](../apps/lore-api/src/work/assembly-line-station/socket-request.test.ts#L69), [validated by answers 404 to a request for /api/auth/me, /api/webhook/github, /api/ws, an escaped /api/%61uth/me and a malformed path @ea76848c](../apps/lore-api/src/work/assembly-line-station/socket-request.test.ts#L76), [validated by keeps the socket open when a route throws @bde615d9](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L517), [validated by answers 404 to /api/../metrics, which leaves the api once its dots are resolved @c1279246](../apps/lore-api/src/work/assembly-line-station/socket-request.test.ts#L93)).
- A `run` or `runs` open may carry no token when the socket has a person, who is resolved again at the open so a signed-out session is refused: a `run` open is admitted when the person's repositories list the run's repository, `not_found` for a run that is gone and `unauthorized` otherwise, and a `runs` open for any person. `plan` and `plan-run` keep their minted tokens, and the token-based open stays for a tab loaded before the change ([validated by reads a run open and a runs open with no token @d600a691](../apps/lore-api/src/work/assembly-line-station/protocol.test.ts#L91), [validated by opens run r1 for Ana's session with no token @d6daeb7f](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L544), [validated by closes run r1 as unauthorized for a socket with neither token nor session @52a91427](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L552), [validated by closes a run in a repo outside Ben's list as unauthorized @b6a496c4](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L564), [validated by opens the runs channel for a session with no token @3fb0372b](../apps/lore-api/src/work/assembly-line-station/runs-channel.test.ts#L212)).

### The run channel and its feed

- A `run` channel opens with a token lore-api minted for exactly that run, or with none for a person's cookie socket *(amended 2026-11-14, see "The socket knows the person")*. A token is minted at `POST /api/assembly-runs/{id}/stream-token`, which no web tier action asks for any more (only the plan editor still has one, for its collab token); the token is bound to the run and the person, only its sha256 is stored in `lore.live_tokens`, it expires after ten minutes, and expired rows are swept as new ones are minted ([validated by mints a token bound to this run and this person @b2bbfaff](../apps/lore-api/src/transport/routes/assembly-lines/run-stream-token.test.ts#L51), [validated by answers 404 for a run that does not exist, minting nothing @099a8d18](../apps/lore-api/src/transport/routes/assembly-lines/run-stream-token.test.ts#L70), [validated by answers 400 to a body without a user @b2a5ab2a](../apps/lore-api/src/transport/routes/assembly-lines/run-stream-token.test.ts#L80), [validated by opens the run it was minted for as Ana @64d29a87](../apps/lore-api/src/integration-tests/live-tokens.test.ts#L32), [validated by opens no other run than the one it was minted for @0c8f4c5f](../apps/lore-api/src/integration-tests/live-tokens.test.ts#L44), [validated by opens nothing once it has expired, and a later mint sweeps it @de4d3c3e](../apps/lore-api/src/integration-tests/live-tokens.test.ts#L59), [validated by answers 404 to a stream token for a run that does not exist @7b27ee95](../apps/lore-api/src/integration-tests/live-socket.test.ts#L174)).
- The channel says `opened`, then delivers the viewer's snapshot, its replay from the cursor the open named, and `catchup_complete`, each as a `frame` envelope; a token minted for another run closes it as `unauthorized`, a run that is gone as `not_found`, a run at its viewer cap as `capacity`, and a wire that falls behind the high-water mark as `slow` — while the socket stays usable ([validated by says opened, then the snapshot and catchup_complete as frames, for a viewer holding this run's token @c87d731f](../apps/lore-api/src/work/assembly-line-station/run-channel.test.ts#L58), [validated by replays from the cursor the open names @4912f21c](../apps/lore-api/src/work/assembly-line-station/run-channel.test.ts#L93), [validated by closes as unauthorized for a token minted for another run, and as not_found for a run that is gone @dba5ab23](../apps/lore-api/src/work/assembly-line-station/run-channel.test.ts#L116), [validated by closes as capacity once the run has its maximum viewers @d536b9e1](../apps/lore-api/src/work/assembly-line-station/run-channel.test.ts#L150), [validated by closes as slow and tells the socket it ended when the wire falls behind @16351b83](../apps/lore-api/src/work/assembly-line-station/run-channel.test.ts#L172), [validated by opens a run channel and delivers its snapshot, replay and catchup_complete as frame envelopes @2e5e172e](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L140), [validated by closes a run channel as unauthorized for a bad token, leaving the socket usable @bba0ee5e](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L266), [validated by opens a run channel with a minted token, catches up, then forwards a transcript row the database notifies @e53c4f7d](../apps/lore-api/src/integration-tests/live-socket.test.ts#L184), [validated by closes a run channel as unauthorized for a token it never minted @f2a12da6](../apps/lore-api/src/integration-tests/live-socket.test.ts#L210)).
- **One feed per assembly run.** The first viewer opens the run's feed, which subscribes ONCE to the notification hub on the run's identity; on every notification it re-reads the named row ONCE and forwards the frame — pod events, transcript rows, task events, CI checks — to every viewer registered for that run. The last viewer to leave closes the feed and its subscription, and the next opens a fresh one ([validated by opens one feed and one hub subscription per run however many viewers join @89b032e5](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L27), [validated by closes the feed and unsubscribes when the last viewer leaves, and opens a fresh one for the next @99744567](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L40), [validated by re-reads a notification once and forwards the frame to every registered viewer @4143d073](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L155), [validated by forwards transcript rows written after catch-up on an agent_event notification, from the feed's cursor @1e31b65e](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L185), [validated by forwards the run's new status and the one task event a notification names @1dfb61a2](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L204), [validated by leaves the feed when the socket closes the channel @10b104b0](../apps/lore-api/src/work/assembly-line-station/run-channel.test.ts#L194), [validated by forwards a live notification to two channels on two sockets, then closes the feed when both close @fad92bcf](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L160)).
- A viewer that joins a live feed catches up on its own — the snapshot, then the replay from ITS cursor — on the feed's one work chain, so a notification that arrives mid-catch-up is handled after it and a late joiner never receives an event twice ([validated by gives a joining viewer its own snapshot and replay from its own cursor @fcd0f1f2](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L81), [validated by does not replay to a late joiner the events the feed already forwarded live to it @5d100f2c](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L105), [validated by handles a notification that arrives during a viewer's catch-up only after it @3a3135e2](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L256), [validated by delivers no live frame to a viewer that joined while a live read was in flight, so its replay still covers every row once @b0da9cb0](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L125)).
- The feed keeps the session's rules: one GitHub read per burst of CI notifications, a re-snapshot of every viewer when the hub resyncs, a viewer dropped alone when it buffers past the high-water mark, a per-run cap of twenty viewers, and every viewer told when a read fails so the next open starts clean ([validated by reads GitHub once per burst of ci_check notifications @7e0f420b](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L228), [validated by re-sends every viewer's snapshot when the notifier resyncs after a lost connection @591d3159](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L273), [validated by ends a viewer that buffers past the high-water mark and keeps the others on the feed @77c041a0](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L290), [validated by refuses a viewer past the per-run cap while keeping the others @db05dbb1](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L63), [validated by ends every viewer with an error and closes the feed when a read fails @d7a6ad26](../apps/lore-api/src/work/assembly-line-station/run-feed.test.ts#L312)).

### The runs channel

- _(Added 2026-10-02.)_ A `runs` channel is the list of the external floor's assembly runs, live ([specs/external-floor](../specs/external-floor/spec.md) FR17). It opens with a token of kind `runs`, and the browser then says which runs are on its page with a `watch` message, which is the one client message a channel kind owns; the server answers with `runs` envelopes that carry a `RunListFrame`: a run started, a run's row, or `resync`. Both are published in OpenAPI beside the run channel's frames. ([validated by reads an open of the runs channel and a watch of two run ids @5e1a22eb](../apps/lore-api/src/work/assembly-line-station/protocol.test.ts#L46), [validated by sends opened, run-1's row, then run_started for run-7 to a browser watching run-1 @3e2df087](../apps/lore-api/src/work/assembly-line-station/runs-channel.test.ts#L98))
- **One feed for the whole list, not one per run.** A list page shows twenty-five runs and a socket holds eight channels, so a channel a row was never an option; and the floor's per-run socket replays a run's whole journal, turns included, which a list has no use for. lore-api keeps one watch on the floor that names the run that started or changed, reads a changed run once, and sends its row to the viewers that have it on their page. ([validated by tells two viewers run-7 started through one floor watch @e0b0dde0](../apps/lore-api/src/work/floor/floor-runs-feed.test.ts#L14), [validated by sends run-1's row to its watcher and nothing to a bystander when run-1 changes @ff7f48d5](../apps/lore-api/src/work/floor/floor-runs-feed.test.ts#L45))
- The browser's client remembers a channel's watch and sends it again on every re-open, so the resubscription after a dropped socket stays the client's work, as it is for every other channel. ([validated by delivers a runs frame and re-sends the watch of run-1 on its own after a drop and reconnect @9ce1cc43](../apps/web-ui/src/lib/live-socket/client.test.ts#L222))
### The plan-run channel *(added 2026-11-06, specs/plan-detail-fast-open FR4)*

- A `plan-run` channel's subject is a plan id, and its token is a `plan-run` live token for that plan, minted at `POST /api/repos/{owner}/{repo}/plans/{id}/run-stream-token` once the web tier has checked the person's session and repo access. A token for another plan is refused as `unauthorized`, and a plan that is gone as `not_found` ([validated by reads a plan-run open of plan p1 with its token, and refuses one without a token @e6eee538](../apps/lore-api/src/work/assembly-line-station/protocol.test.ts#L76), [validated by closes with unauthorized for a token minted for plan p2, joining no feed @8a1c771d](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L139), [validated by closes with not_found for a plan that is gone @ba328139](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L151)).
- On open, lore-api picks the plan's run by the page's rule (open, else newest not cancelled, else newest) from both engines' runs, read with no cost, and sends a `plan_run` message with the run's facts: its status, user story, spec PR (with GitHub's title and open thread count) and the spec analysis's question. It sends `run: null` when no run has started, and never in place of a failure: a list it can't read closes the channel as `server` ([validated by sends run-2's facts with spec PR #7's title and threads, then joins run-2's feed @d71dae3c](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L197), [validated by sends a null plan_run for a plan no run has started for, and joins no feed @7b5a4e41](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L161), [validated by throws when the plan's runs can't be read, sending no null plan_run in place of the failure @3a35cb47](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L173)).
- The channel then joins the run's feed like a `run` channel, and forwards its frames as `frame` envelopes, except `agent_event` and `ci_check`: the plan page draws neither, and the `plan_run` facts carry the spec PR ([validated by forwards the feed's run_status and node_status but no agent_event and no ci_check @6d4e5aa3](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L221), [validated by opens plan p1's plan-run channel: opened, the run's facts with its spec PR, then its status and visits with no agent event and no ci_check @f6447c3f](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L426)).
- Once the feed has caught up, a visit that settles or a change of the run's status makes the channel read the facts again, once per 300 ms burst, and send `plan_run` only when they changed ([validated by re-reads the facts once for a burst of two settling visits after catch-up, and sends plan_run only when they changed @3c306ba5](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L242), [validated by does not re-read the facts for the visits the feed's snapshot replays before catch-up @748fc82f](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L261)).
- It follows the plan across runs. Every open `plan-run` channel shares one viewer of the floor-wide feed the `runs` channel already keeps. lore-api reads each started run once and hands it only to the channels watching its plan, which leave the old run's feed, send `plan_run` for the new run and join its feed. A gap in the floor's feed, or a started run it can't read, makes every channel pick its run again ([validated by reads run-9 once for two channels on plan p1 and tells both, and not the channel on plan p2 @df1436c7](../apps/lore-api/src/work/assembly-line-station/plan-run-watch.test.ts#L51), [validated by joins the floor's feed once for every channel, and leaves it when the last one stops @ba7e3383](../apps/lore-api/src/work/assembly-line-station/plan-run-watch.test.ts#L81), [validated by switches to run-2 when it starts: leaves run-1's feed, sends run-2's facts, joins its feed, and drops a late frame of run-1 @0a26e6f4](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L272), [validated by asks for the plan's runs again on a resync and moves to the run it now picks @d2594ab0](../apps/lore-api/src/work/assembly-line-station/plan-run-channel.test.ts#L290), [validated by asks every channel to resync when a started run can't be read @a561e820](../apps/lore-api/src/work/assembly-line-station/plan-run-watch.test.ts#L116)).
- The browser opens it like a `run` channel, with a token fetched fresh for every open, and hands each `plan_run` to the channel's `onPlanRun` ([validated by opens plan p1's plan-run channel with a fresh token on each open and delivers its plan_run, then reopens with a new token after a drop @ac561e32](../apps/web-ui/src/lib/live-socket/client.test.ts#L336)).

### The plan channel

- A `plan` channel is the collaboration server's connection wearing the socket's face: the server sees an object whose `send` becomes a `data` envelope and whose `close` becomes a `closed` one, the client's `send` envelopes become its inbound messages, and the client closing the channel tells the collaboration server the client left, once. Auth stays where it was — the Hocuspocus handshake inside the tunnel carries the plan's collab token — so a minted token authenticates and a forged one is refused with the library's own permission-denied message ([validated by says opened, hands client bytes to the collaboration server and tunnels its replies back as data @661ffade](../apps/lore-api/src/work/assembly-line-station/plan-channel.test.ts#L56), [validated by tells the collaboration server the client closed, once, when the socket closes the channel @e1d13e01](../apps/lore-api/src/work/assembly-line-station/plan-channel.test.ts#L75), [validated by relays a server-side close as a closed envelope with its code, unauthorized for 4401, and ends the channel @cbbfc2ff](../apps/lore-api/src/work/assembly-line-station/plan-channel.test.ts#L85), [validated by tunnels plan bytes both ways and relays the collaboration server's close @bba0ee5e](../apps/lore-api/src/work/assembly-line-station/live-socket.test.ts#L210), [validated by tunnels the plan collaboration handshake: a minted collab token is authenticated, a forged one is refused, and the client can close the tunnel @c4d030b5](../apps/lore-api/src/integration-tests/live-socket.test.ts#L228)).

### The browser side

## Consequences

- The SSE route `GET /api/assembly-runs/{id}/stream`, the web-ui's session-authenticated SSE proxy and the `EventSource` hook are deleted. The browser reaches lore-api's socket directly at its public host, as the plan editor already did *(amended 2026-11-14: on the UI's own host, `lore.gcp.re-cinq.com/api/ws`, which the ingress routes to lore-api, so the session cookie rides the upgrade)*; the web-ui nginx ingress and its 60-second read timeout are no longer on the path.
- The run stream's contract, cursor semantics and Postgres `NOTIFY` fan-out are unchanged; ADR-037's amendments on those points stand. What changed is who listens: one feed per run instead of one session per connection, so a run with N viewers costs one re-read per notification instead of N.
- `LORE_PLANS_WS_URL` becomes `LORE_WS_URL` (`wss://<the UI's host>/api/ws`). Terraform sets it; CI never runs terraform, so the apply must land with the deploy.
- lore-api still runs one replica while plans are live (ADR-047). The run channel is fan-out-safe across replicas, but both channels share one socket, so scaling lore-api needs sticky routing for the socket, not only for plans. No planning-station change was needed for this: the library's `/api/plans/collab` mount stays on the listener, and lore-api tunnels to the same Hocuspocus instance the planning registration returns.
- The plan and run channels live in one feature folder, `apps/lore-api/src/work/assembly-line-station/`, together with the run stream's frames, session reads and notification hub.

## Alternatives

**Keep SSE for runs and only share the plan socket.** Rejected: the plan page and the run page are one flow, and two transports means two reconnect state machines, two auth ceremonies and a proxy hop for one of them.

**Make each run a Hocuspocus document and use its stateless messages.** Rejected: the run stream would depend on the collaboration library's wire protocol and hooks, and a planning-station change would be needed to let non-plan document names through its authenticator. The tunnel needs neither.

**Binary frames with a channel prefix instead of base64 in JSON.** Rejected for now: Yjs updates are small and the first document load is the only large message; one text framing keeps the protocol readable and the OpenAPI contract complete. Revisit if plan documents grow.
