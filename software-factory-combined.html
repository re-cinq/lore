How work enters Lore’s assembly lines

An approved feature plan becomes a specification. A reported bug starts with triage. Either route can produce a ticket with a testable outcome.

Feature planning

Agree on what to build

The team refines the plan with Lore. After approval, Lore writes a specification, checks it against the plan and opens a pull request.

Spec tickets

Turn a merged spec into work

Lore splits the spec into stories and tasks, checks what already exists, and creates or updates GitHub issues for the work that remains.

Issue triage

Decide which bugs to fix

Lore checks the report against the code and tries to reproduce it. The team decides whether to prioritize a confirmed bug. A broad fix can become several tasks.

For a new repository, the onboarding line prepares its workflows and templates in one pull request for review.

Two routes to a prioritized ticket

If implementation stalls

Implemented. Lore records the blocker on the ticket for the team.

Design goal. Feed those findings into the plan automatically and retry with a smaller ticket.

One ticket becomes a tested pull request

The implementation line starts with a concrete example of success. The repository’s own checks judge each change before the pull request leaves draft.

Define done

Turn the ticket into a failing test

Lore reads the ticket and its context, writes acceptance tests for the missing behavior and opens a draft pull request with those tests.

Build

Make one behavior pass at a time

In each round of test-driven development (TDD), an agent writes a test, makes it pass and refactors. Each push runs continuous integration (CI). A failure guides the next round or a targeted repair.

Review tests

Check what the tests would catch

Once CI passes, a separate reviewer looks for missing cases, such as invalid input or a failed write. Findings can send the change back for another round.

Ready for review

Hand the change to reviewers

Lore describes the change, updates the branch and takes the pull request out of draft. It can still repair failing checks or address review findings.

How a draft moves forward

Example from the quote API. A customer enters an invalid discount code. The acceptance test expects the API to return HTTP 422. Product can review that promise and engineering can run it.

When the line stops early

If a merged change already satisfies the ticket, Lore can close it with the evidence. If the work is unclear or repeated repairs fail, Lore records the blocker for a person to resolve.

Who reviews the change and who can merge it?

Review produces a verdict on the pull request. A separate auto-merge line can act on that verdict when the repository enables it.

Code review

Review the proposed change

Lore reads the diff against the spec, repository conventions and CI results. It posts its findings and verdict on the pull request.

Reply

Address requested changes

When a teammate requests changes, Lore can make a fix and reply in the original thread. A question that needs a product or engineering decision stays with the team.

Recheck

Review what changed after a push

The recheck examines new commits and revisits earlier findings so reviewers can see what was resolved.

Review pilot. Selected repositories can run a second, five-pass review alongside the standard review. Its findings are advisory.

Merge decisions in Lore today

Ready to merge?CI passes, review threads are resolved, Lore’s approval covers the latest commit and the configured waiting period has elapsed.
Who approves?GitHub’s branch rules govern approval. Lore can merge directly or enable GitHub auto-merge. Required code-owner or independent approvals still apply.
After mergeFor a tracked task, Lore records the merge, closes the linked issue and saves the outcome for future work.

Design goal · risk-based routing

The proposed lights-out mode would merge every ready change automatically. Outside that mode, a risk check would send low-risk changes to auto-merge and high-risk changes to a person.

Design goal · Did the release solve the product problem?

Today, a daily Slack digest and a weekly changelog summarize delivery, and weekly spec upkeep opens corrections for review. The proposed release check below would measure the effect on users.

Proposed check after release

The check runs on its ownWorked · didn't work · can't tell · something got worse
People decide what to doThe check gives a result, not a decision
If something got worse, the system actsFlag off, roll back. That is safety, not judgement

Six things each change declares in its plan

signal the one measure that shows whether the change worked

who who the change applies to

guardrail what must not get worse

how-far how much the signal should move

how-long how long we watch before calling it

attribution how we tell this change apart from the rest

Saved to the knowledge base, without flooding it

When something happensA release, a merge, an incident, a result
Regular summariesOne per component, never the raw stream
Only if it says something new"Nothing changed" is not worth saving
written by peopleWhy we chose this, what a result means, what went wrong. The factory asks at the time; nobody writes it up later

What it changes for planning

How past changes turned outTargets are argued from what happened before
Changes that did not workCome back as new work, with the evidence attached
Things that worked more than onceBecome a starting template
What past work cost and tookSays what this one will likely cost, before we commit

A shared memory for the software factory

Agents can read the repository in front of them. The knowledge base holds everything else the company knows: other services, tickets, decisions, deployments, owners and rules, connected across every repo. Local code always wins.

solid = parsed from source data · dashed amber = inferred by AI, with evidence
Why agents can trust it. Every fact records its source, whether it is approved, parsed or AI-inferred, and when it stopped being true. Across every layer: a model gateway to the customer's approved LLM, mirrored permissions, one isolated instance per customer.
LayerWhat it does
SourcesGit host, tickets, docs, CI/CD, ownership, incidents and factory run records. The proposed release check would add its results.
IngestionRead-only connectors, secrets and personal data removed, kept current by webhooks and a nightly sync
ProcessingCross-repo facts linked through shared IDs; AI summaries and decisions only with evidence; conclusions, never raw monitoring data
StorageKnowledge graph and text search, plus versioned plans, specs, decisions and conventions in Git
Context serviceOne endpoint, six tools: task context, consumers, owners, conventions, similar changes, past outcomes. Permission filtering and an audit log
ConsumersPlanning and implementation use shared context. The proposed risk and release checks would also use it. Agents get context at session start.
