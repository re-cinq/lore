Define done as failing tests, then one round per agent

The ticket is turned into acceptance tests that fail today. When they pass, the ticket is finished and nothing more is owed. Each later visit is a fresh agent doing one round, and the PR's build grades it, never the agent.

define-done

Write the red acceptance tests agent

Reads the ticket and any spec it points to. Writes the fewest tests that mean "done": one is ideal, more than five means the ticket needs splitting. Proves each fails because the behaviour is missing. Writes no production code. Picks exactly one strategy: direct · parallel-change · characterize · mechanical.

open-pr

Push and open a draft PR agent

Pushes the tests and the dod.md brief, then opens a draft pull request, which gives CI something to judge and keeps code review quiet.

tdd-round

One red-green-refactor round agent

Writes one failing test for the smallest open facet, the least code that passes it, then refactors. Ticks the facet and pushes. Never edits an acceptance test to make it pass.

repair-build

Repair a stuck build agent

Used when the build stayed red and the round pushed nothing. Gets the failing checks from CI and fixes only those.

The agent doesn't run lint, typecheck or the full suite. CI already runs all of it on every push, so the agent runs only the tests it's working on.
Twelve rounds is the limit on purpose. A ticket that needs more was sized wrong, so running out is itself the finding.

Leaves this stage

  • →CI is green: on to review and approval.
  • ✕The ticket can't be expressed as tests, out of rounds, or a repair failed: blocked, with the reason on the ticket.
  • ✓The ticket is already resolved: ticket and draft PR are closed with the reason.

Out of draft, reviewed, merged by risk

The PR gets a real description and leaves draft, which starts code review. Once it is ready, two questions decide whether the factory merges it or a human does.

ready-for-review

Describe the finished work agent

Reads the diff against dod.md and writes the PR description and a new title, including why it strayed from the planned strategy, if it did. Removes dod.md and takes the PR out of draft.

await-pr

Wait for CI and review waits on CI

Resumes when CI is green on the latest commit and every review thread is resolved.

fix-ci

Fix a red build agent · max 3

Starts from CI's report: the failing checks, their annotations and the failed step. Fixes only those, pushes, and goes back to waiting.

The check that runs after release, and what it feeds

Acceptance criteria say the software does what we asked for. This check says we asked for the right thing. Its conclusions, not the data, go into the knowledge base and into the next plan.

What happens after release

The check runs on its ownWorked · didn't work · can't tell · something got worse
People decide what to doThe check gives a result, not a decision
If something got worse, the system actsFlag off, roll back. That is safety, not judgement

Six things each change declares in its plan

signal the one measure that shows whether the change worked

who who the change applies to

guardrail what must not get worse

how-far how much the signal should move

how-long how long we watch before calling it

attribution how we tell this change apart from the rest

Saved to the knowledge base, without flooding it

When something happensA release, a merge, an incident, a result
Regular summariesOne per component, never the raw stream
Only if it says something new"Nothing changed" is not worth saving
written by peopleWhy we chose this, what a result means, what went wrong. The factory asks at the time; nobody writes it up later

What it changes for planning

How past changes turned outTargets are argued from what happened before
Changes that did not workCome back as new work, with the evidence attached
Things that worked more than onceBecome a starting template
What past work cost and tookSays what this one will likely cost, before we commit

A shared memory for the software factory

Agents can read the repository in front of them. The knowledge base holds everything else the company knows: other services, tickets, decisions, deployments, owners and rules, connected across every repo. Local code always wins.

solid = parsed from source data · dashed amber = inferred by AI, with evidence
LayerWhat it does
SourcesGit host, tickets, docs, CI/CD, ownership, incidents, release check results and factory run records
IngestionRead-only connectors, secrets and personal data removed, kept current by webhooks and a nightly sync
ProcessingCross-repo facts linked through shared IDs; AI summaries and decisions only with evidence; conclusions, never raw monitoring data
StorageKnowledge graph and text search, plus versioned plans, specs, decisions and conventions in Git
Context serviceOne endpoint, six tools: task context, consumers, owners, conventions, similar changes, past outcomes. Permission filtering and an audit log
ConsumersPlanning, the implementation agents, the risk assessment and the release check all query the same service; agents also get context at session start
Why agents can trust it. Every fact records its source, whether it is approved, parsed or AI-inferred, and when it stopped being true. Across every layer: a model gateway to the customer's approved LLM, mirrored permissions, one isolated instance per customer.
